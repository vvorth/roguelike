# T13 — Stair tiles and level stair fields
Status: todo
Depends on: none

## Goal
Add the two staircase tiles and the fields that let a level record where its stairs are, so the
dungeon can become multi-level.

## Context
This is an interactive terminal roguelike engine with ASCII graphics, similar in feel to ADOM.
Versions 1 and 2 are complete and passing 1300 tests: it generates one dungeon level of rooms
and corridors, lets you walk an `@` around it with permissive field of view and fog of war,
opens doors by bumping them, renders in 256 colour, and quits cleanly.

Version 3 makes the dungeon **multi-level**: the player spawns on an up-staircase, finds a
down-staircase, descends, and the next level is generated with its up-staircase at exactly the
coordinate the player left from — so the two levels line up. You are adding the vocabulary
that makes that possible. Everything else in v3 is expressed in terms of what you produce, so
this is the foundation task.

The engine is built by independent workers who never communicate; a frozen contract defines
every seam. One other worker is running in parallel on unrelated leaf modules.

Two things about this codebase you must not fight:

- **`Level` is a frozen dataclass** with a tuple-of-tuples grid. That is deliberate: it makes
  "the renderer must never mutate game state" a guarantee the interpreter enforces. Your new
  fields are frozen too.
- **`Tile` has had exactly three members since v1**, and two tests assert the tile tables by
  exact equality. Those tests are **yours** and must be *extended*, not deleted.

You are the only worker who edits `level.py` in v3 — it has not changed since v1.

Out of scope, explicitly — do not build, do not stub: monsters, combat, items, inventory,
save-load, sound. No trap doors, no portals, no locked stairs, no level "themes". Do not place
stairs (that is the generator's job, another task) and do not write any descent logic. You add
vocabulary and data fields, nothing more.

Coordinates are `(x, y)`, origin top-left, `y` grows **down**, grid storage `grid[y][x]`.

## Produce

`roguelike/tiles.py` (amend):
```python
class Tile(IntEnum):
    WALL = 0; FLOOR = 1; DOOR = 2
    STAIRS_UP = 3
    STAIRS_DOWN = 4

TILE_CHARS: dict[Tile, str]      # + STAIRS_UP: "<", STAIRS_DOWN: ">"
WALKABLE: frozenset[Tile]        # + both stair tiles
STAIRS: frozenset[Tile]          # NEW — {STAIRS_UP, STAIRS_DOWN}
```

`roguelike/level.py` (amend) — three fields **appended with defaults**, so every existing
positional construction keeps working:
```python
@dataclass(frozen=True)
class Level:
    width: int
    height: int
    grid: tuple[tuple[Tile, ...], ...]
    rooms: tuple[Room, ...]
    player_start: tuple[int, int]
    seed: int
    stairs_up: tuple[int, int] | None = None
    stairs_down: tuple[tuple[int, int], ...] = ()
    depth: int = 1
```

`tests/test_level.py` (extend).

`stairs_down` is a **tuple, not a single coordinate** — the tuple shape is the scaffolding for
future dungeon branching. It will hold exactly one entry for now, but do not collapse it.

## Constraints
- Python 3.10+, **standard library only**. `from __future__ import annotations` stays.
- `tiles.py` imports nothing from the project; `level.py` imports only `roguelike.tiles`.
  No `curses` in either.
- Both stair tiles are **walkable** — add them to `WALKABLE`. This is load-bearing: it is what
  makes stairs passable and transparent everywhere else in the engine **without touching
  `world.py`, `fov.py` or `movement.py`**, because those are defined in terms of `WALKABLE` and
  "not `WALL`". Do not edit those files to add stair handling; if you think you need to, you
  have made a mistake.
- Enum values are binding: `STAIRS_UP = 3`, `STAIRS_DOWN = 4`. Do not renumber the existing
  three.
- Glyphs are binding: `<` up, `>` down. `TILE_CHARS[Tile.DOOR]` stays `"+"`.
- `Level.__post_init__` gains three checks, all raising `ValueError`: `depth < 1`; `stairs_up`
  is not `None` and not in bounds; any `stairs_down` entry not in bounds. It must **not**
  require stairs to exist — hand-built test levels with no stairs must stay constructible, and
  many existing tests rely on that.
- Do not add a `Tile.STAIRS` member, a `is_stairs_tile()` helper beyond the `STAIRS` frozenset,
  or any stair-placement logic. Do not add fields beyond the three specified.
- The existing 85 tests in `tests/test_level.py` must still pass, except the two that assert
  the tile tables by exact equality — **extend those assertions to include the new tiles**.
  Do not delete them; they are the guard that the tables stay in sync.
- Tests must not initialise curses and must pass with no TTY. No `conftest.py`.

## Acceptance criteria
- `Tile` has exactly five members with values `WALL=0, FLOOR=1, DOOR=2, STAIRS_UP=3,
  STAIRS_DOWN=4`.
- `TILE_CHARS` equals exactly `{WALL:"#", FLOOR:".", DOOR:"+", STAIRS_UP:"<", STAIRS_DOWN:">"}`
  — asserted by equality, so a future addition cannot slip in unnoticed.
- `WALKABLE` equals exactly `frozenset({FLOOR, DOOR, STAIRS_UP, STAIRS_DOWN})`; `WALL` is not
  in it.
- `STAIRS` equals exactly `frozenset({STAIRS_UP, STAIRS_DOWN})` and is a `frozenset`.
- `is_walkable_tile` is `True` for both stair tiles.
- `tile_char` returns `<` and `>` for the stair tiles and still raises `KeyError` for a value
  absent from the table.
- A `Level` built with **no** stair arguments works and reports `stairs_up is None`,
  `stairs_down == ()`, `depth == 1` — this is what keeps every existing test valid.
- A `Level` built positionally with all nine fields works, and field order matches the contract
  via `dataclasses.fields`.
- `Level` with `depth=0` or `depth=-1` raises `ValueError`; `depth=1` is fine.
- `Level` with `stairs_up` out of bounds raises `ValueError`; with `stairs_up=None` does not.
- `Level` with any out-of-bounds entry in `stairs_down` raises `ValueError`; `stairs_down=()`
  does not; a two-entry `stairs_down` with both in bounds is accepted (the branching shape must
  already work).
- `Level` remains frozen: assigning to `stairs_up`, `stairs_down` or `depth` raises
  `dataclasses.FrozenInstanceError`.
- A grid containing stair tiles reports them from `tile_at`, and `is_walkable` is `True` for
  those cells — proving the stair tiles flow through the existing predicate unchanged.
- `is_walkable` is still `False` out of bounds and still never raises.
- All 85 pre-existing tests still pass, with the two table-equality assertions extended.
- `tiles.py` and `level.py` still import nothing outside the stdlib and `roguelike.tiles`,
  asserted by parsing the source with `ast`. Neither imports `curses`.
