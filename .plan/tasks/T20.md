# T20 — Planning passability and activity planners
Status: todo
Depends on: T19

## Goal
Decide, for each kind of multi-turn action, which cell the character should step to next —
using only what the character has actually seen.

## Context
This is an interactive terminal roguelike engine with ASCII graphics, similar in feel to ADOM.
Versions 1–3 are complete and passing 1666 tests: a procedurally generated multi-level dungeon,
permissive field of view, fog of war, openable doors, colour.

Version 4 adds automatic navigation. You own the two planners at the heart of it:

- **Auto-explore** — walk the level until there is nothing left to discover.
- **Auto-walk** — walk in a direction until something interesting happens; in a corridor,
  follow its turns and stop at a fork or where it opens into a room.

You also add one predicate to `world.py`. Another worker wires your planners into the turn loop;
a third built the pathfinder you will use.

The engine is built by independent workers who never communicate; a frozen contract defines
every seam.

### The rule that defines this task

**Auto-explore must not cheat.** It explores from the character's perspective, using only
`explored`. A worker who consults the full grid will produce beautiful coverage numbers and
will have failed the task. The contract states this and the tests must prove it.

The classic answer is *frontier* search: repeatedly walk to the nearest explored cell that
touches something unexplored. Prototyped against the real engine before this task was written,
it reached **100% of walkable tiles on all five sample seeds**, every run ending by exhausting
frontiers rather than hitting a cap, at about 2 ms of planning per turn against a 100 ms budget.

### The two details that make it work, and their failure modes

1. **A closed door must be traversable when planning.** Bumping it opens it, so a route may be
   planned through it. Without this, every frontier behind a door is unreachable and
   **auto-explore stalls in the first room** — which looks like a mysterious early stop, not a
   bug. This is why `world.is_planning_passable` exists.
2. **A closed door is itself a frontier**, because it hides whatever lies beyond regardless of
   how much is mapped around it. Without this, auto-explore walks past unopened doors and
   declares the level finished.

Out of scope, explicitly — do not build, do not stub: monsters, items, combat, save-load. No
auto-descend (auto-explore stops on the current level, by user decision). No travel between
levels. No path caching or incremental replanning — re-planning every turn is affordable.
No `advance`, no `GameState`, no turn loop: another task owns those. Extra surface is a defect,
not initiative.

Coordinates are `(x, y)`, origin top-left, `y` grows **down**.

### `frontier_cells`
A cell is a frontier iff it is in `explored`, satisfies `is_planning_passable`, and either
touches (8-directionally) an **in-bounds cell not in `explored`**, or **is itself a closed
door**.

### `walk_step` → `(next_coord, reason)`
`reason` is `"blocked"`, `"intersection"`, `"opening"`, or `""` when moving.

- **In the open** (`is_wide(passable, *position)`): next is `position + direction`; stop
  `"blocked"` if it is not passable. Wide areas never follow turns.
- **In a corridor** (not wide): candidates are the passable **orthogonal** neighbours excluding
  `came_from`. Exactly one → move; more than one → stop `"intersection"`; none → stop
  `"blocked"`.
- **Stop before a room**: if the chosen next cell `is_wide`, stop `"opening"` **without moving
  onto it**.
- The first step has `came_from is None` and uses `direction`.

## Constraints
- Python 3.10+, **standard library only**. `from __future__ import annotations` at the top.
- `activity.py` imports **only** `roguelike.level`, `roguelike.world`, `roguelike.pathfind`.
  It must **not** import `game`, `render`, `keys` or `events`. No `curses` in either module.
- `world.py` keeps its existing imports; add the one function and nothing else. **Do not modify
  `is_passable`, `is_transparent` or `is_closed_door`** — actual movement and sight must keep
  using them, and only planning uses the new one.
- `Activity` is `frozen=True`; `ActivityKind` uses `auto()`.
- Both planners are **pure**: no mutation of any argument, no I/O, no module-level state, no
  caching, and **no dependence on set iteration order** in anything that affects the result.
  `frontier_cells` returns a `frozenset`, so ordering cannot leak — but do not let it leak into
  a choice either.
- **`frontier_cells` must read only `explored`**, plus bounds and the tile identity of cells
  already explored. It must never consult a tile that is not in `explored`.
- Do not implement the walk as a loop over many turns. `walk_step` decides **one** step; the
  turn loop calls it repeatedly.
- Do not add an `Activity.path` field or cache a route on the activity — routes are re-planned
  each turn.
- Tests must not initialise curses and must pass with no TTY. Hand-built `Level`s from
  character grids are the right tool for the unit tests; you **may** import
  `roguelike.generator` in `tests/test_activity.py` for the end-to-end coverage test, since the
  claim being verified is about real levels.
- No `conftest.py`. The existing 26 tests in `tests/test_world.py` must still pass.

## Acceptance criteria

**`is_planning_passable`**
- `True` for floor, for an open door, and for a **closed** door; `False` for wall and for every
  out-of-bounds coordinate; never raises.
- It differs from `is_passable` on exactly one case — the closed door — asserted directly.
- `is_passable`, `is_transparent` and `is_closed_door` are unchanged in behaviour; the existing
  `tests/test_world.py` cases still pass.

**`frontier_cells`**
- On a hand-built level where a small area is explored, the returned set is exactly the
  explored, planning-passable cells touching unexplored ground — compared against a literal
  expected set.
- A **closed door inside the explored region is a frontier** even when every cell around it is
  explored. Open the door (add it to `open_doors`) and, with the far side still unexplored, it
  is still a frontier via its unexplored neighbours; explore the far side too and it is no
  longer a frontier.
- A fully explored level with no closed doors yields an **empty** frontier set.
- Cells not in `explored` are never returned; walls are never returned.
- **The no-cheating test:** build two levels identical inside the explored region but different
  outside it, and assert `frontier_cells` returns the **same** set for both. A implementation
  that peeks at unexplored terrain fails this. This is the most important test of the task.
- Returns a `frozenset`; the inputs are unmodified.

**`walk_step`**
- Straight corridor: follows it, `reason == ""`, and `came_from` prevents walking back.
- Corridor with a bend: **follows the turn** even though `direction` no longer points that way.
- Dead end: `(None, "blocked")`.
- T-junction in a corridor: `(None, "intersection")`, and the player has **not** moved.
- Corridor opening into a room: `(None, "opening")`, and the returned coord is `None` so the
  character stops **before** entering — assert the room cell is not returned.
- In the open: walks straight in `direction`, ignoring side openings, until `(None, "blocked")`.
- `direction == (0, 0)` in the open → `(None, "blocked")`.
- First step with `came_from is None` uses `direction` in a corridor too.

**End to end, on real levels**
- Driving `frontier_cells` + `pathfind.find_path` + the real engine's movement over at least
  three generated seeds explores **≥ 95%** of walkable tiles and terminates by frontier
  exhaustion, not a turn cap. *Reference measurement: 100% on five seeds.* Use a turn cap in the
  test only as a failsafe and assert it is not reached.
- Planning cost per turn stays well under 100 ms — assert with a generous margin.
