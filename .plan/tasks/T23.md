# T23 — Point-to-point line of sight
Status: todo
Depends on: none

## Goal
Add one function to `fov.py`: an exact "can A see B?" test that is cheap enough to call once per
monster per turn. Change nothing else in the module.

## Context
This is an interactive terminal roguelike engine with ASCII graphics, similar in feel to ADOM.
Versions 1–4 are complete and passing **1982 tests**: a procedurally generated multi-level
dungeon, field of view, fog of war, doors, colour, diagonal movement, pathfinding and automatic
navigation.

Version 5 adds monsters. Every monster needs to ask, every turn, "can I see the player?" — and
that question is asked far more often than the existing whole-field-of-view computation was
designed for.

The engine is built by independent workers who never communicate; a frozen contract defines
every seam. Two other workers are running in parallel on unrelated modules.

### Why this is a separate function and not a call to `compute_visible`

Measured on this build, on an 80×22 level:

| Approach | 30 checks |
|---|---|
| `compute_visible(radius=20)` then membership test | **218.8 ms** |
| A dedicated point-to-point check | **5.0 ms** (0.167 ms each) |

**44× cheaper.** The naive approach blows the turn budget at about 14 simultaneous checks, and
version 5 puts six monsters on every level, each checking every turn. The reason is simple:
`compute_visible` computes visibility for the entire radius-20 disc, and an awareness check
cares about exactly one target cell.

Your function computes opacity over **the bounding box of the two points, grown by one cell**,
and nothing else. That is the whole optimisation.

### The constraint that makes this task opus-grade

**`compute_visible` must not change behaviour — at all.** `tests/test_activity.py` is a **frozen
file that no version-5 worker may edit**, and it drives the real `fov.compute_visible` end to
end at lines 769 and 808 as part of a full auto-explore run. If you perturb `compute_visible`,
you break a test you are not allowed to fix, and the whole increment stalls. This exact failure
mode happened in version 3 and is on record.

So: your work is **purely additive**. You may read `compute_visible` and `_segment_is_clear` and
reuse `_segment_is_clear` and `_SAMPLE_OFFSETS`. You may not alter their behaviour. Refactoring
that "cleans up" shared code is the highest-risk thing you could do here; if you find yourself
wanting to, don't.

Out of scope, explicitly — do not build, do not stub: monsters, AI, combat, a radius parameter
on the new function, a symmetric-LOS helper, caching, a "fast mode", Bresenham or any
approximation, or changes to `DEFAULT_RADIUS`. Extra surface is a defect, not initiative.

Coordinates are `(x, y)`, origin top-left, `y` grows **down**.

## Produce

Add to `roguelike/fov.py`:
```python
def has_line_of_sight(level: Level, open_doors: frozenset[tuple[int, int]],
                      observer: tuple[int, int], target: tuple[int, int]) -> bool
```

Extend `tests/test_fov.py`. `__all__` gains `"has_line_of_sight"`.

### Semantics — binding
- Eye at the **observer's** cell centre, `(ox + 0.5, oy + 0.5)`, exactly as `compute_visible`
  places it.
- The **eight sample points** on the `target` cell — four corners and four side midpoints — the
  same `_SAMPLE_OFFSETS` the module already defines.
- `True` iff **at least one** segment from the eye to a sample point crosses no opaque cell,
  under the identical rules `_segment_is_clear` already implements: the observer's cell and the
  target cell are exempt from the opacity test, and the diagonal-corner rule blocks only where
  both flanking cells are opaque.
- Opacity comes from `world.is_transparent` and nowhere else. This module does not look at tiles
  and does not know the closed-door rule.
- **Opacity is snapshotted over the bounding box of `observer` and `target`, grown by one cell
  in each direction and clipped to the level.** Never the whole radius disc. Cells outside the
  snapshot read as opaque, exactly as `compute_visible`'s own snapshot does.
- `has_line_of_sight(level, doors, a, a)` is `True`.
- **No radius parameter.** Range limiting is the caller's business.
- Out-of-bounds coordinates return `False` rather than raising.

> **Binding argument order: `(observer, target)`.** Permissive line of sight is **not
> symmetric** — measured on this build, **2 of 720 cell pairs (0.28%) disagree** about who can
> see whom, because the eye sits at a cell *centre* while the target is tested at eight
> *boundary* samples. Callers always ask `(npc_position, player_position)`. Swapping the
> arguments is a real behaviour change, not a refactor, and it will be wrong 0.28% of the time —
> which is exactly often enough to be a bug nobody can reproduce.

## Constraints
- Python 3.10+, **standard library only**. No new imports beyond what `fov.py` already has.
- `fov.py` may import only `roguelike.level` and `roguelike.world`. No `curses`.
- **No floating point.** Use the same doubled-integer scheme the module already uses: every
  coordinate of interest is a multiple of 0.5, so doubling makes them all integers and the
  answer is exact with no epsilon.
- **`compute_visible`, `_segment_is_clear`, `_SAMPLE_OFFSETS` and `DEFAULT_RADIUS` keep their
  current behaviour exactly.** You may reuse `_segment_is_clear` and `_SAMPLE_OFFSETS`
  unchanged; you may add a private helper. You may **not** change their signatures or logic.
- Pure: no mutation of any argument, no I/O, no module-level mutable state, **no caching across
  calls**, no dependence on set iteration order.
- Do not add a radius parameter, a `symmetric=` flag, an approximation switch, or a public
  helper beyond the one function.

## Acceptance criteria
- **A regression guard on `compute_visible`, written first.** Over at least two generated levels,
  compute `compute_visible` for a good spread of origins (say 40+) and assert the results equal a
  set of expected values captured from the current implementation — or, more simply and more
  robustly, assert a rich set of structural properties that would break under any behavioural
  change: origin always present, symmetry of the wall ring around a room, exact cell counts at
  two radii, and behaviour with a door open versus closed. The point is that a reviewer can see
  this test would fail if `compute_visible` drifted.
- `has_line_of_sight(level, doors, a, a)` is `True` for floor, wall and closed-door cells alike.
- **Agreement with `compute_visible`:** for several origins on a generated level, and for every
  cell within radius 20, `has_line_of_sight(level, doors, origin, cell)` equals
  `cell in compute_visible(level, doors, origin, 20)`. This is the criterion that proves you
  reused the geometry rather than reimplementing it differently. *Note: this must hold because
  both use the same observer-at-centre convention — if it fails, your bounding box is too tight,
  which is the most likely bug in this task.*
- **The bounding box is not too tight:** construct a case where the clear line between two cells
  bulges outside their tight bounding rectangle, and assert the answer still matches
  `compute_visible`. A one-cell margin is required; assert a case that fails without it.
- Two cells in the same open room see each other. Two cells separated by a wall do not.
- A **closed** door blocks sight; the **same** door open does not. Assert both with the same
  coordinates, varying only `open_doors`.
- Sight is **not** blocked by distance — a clear corridor 30 cells long is visible end to end,
  since there is no radius parameter.
- **The asymmetry is real and is a defined behaviour:** find at least one pair `(a, b)` on a
  generated level where `has_line_of_sight(a, b) != has_line_of_sight(b, a)`, and assert it, so
  that the argument order is pinned by a test and a future "symmetry fix" is loud. (Search a
  sample of pairs to find one; roughly 1 pair in 360 qualifies.)
- Out-of-bounds observer or target returns `False` and never raises. Negative coordinates too.
- **Performance:** 30 checks between random floor cells on an 80×22 level complete in well under
  50 ms — measured in the test with a generous margin so it is not flaky. *Reference measurement:
  5.0 ms.* Also assert it is **substantially faster** than 30 `compute_visible` calls, since
  that speed difference is the entire reason this function exists.
- `fov.__all__ == ["DEFAULT_RADIUS", "compute_visible", "has_line_of_sight"]`.
- `fov.py` imports only `roguelike.level` and `roguelike.world`, and no `curses` — assert with
  `ast`. No float literal in the new code.
- Tests do not initialise curses and pass with no TTY. No `conftest.py`.
