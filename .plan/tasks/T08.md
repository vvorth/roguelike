# T08 — Style vocabulary and palette
Status: todo
Depends on: none

## Goal
Define the colour and visibility vocabulary — which semantic role each glyph plays, and what
attribute it gets at each visibility level — as pure data with no terminal involvement.

## Context
This is an interactive terminal roguelike engine with ASCII graphics, similar in feel to ADOM.
Version 1 is complete and passing 912 tests: it generates a dungeon of rooms and corridors,
walks an `@` around it, and quits cleanly, in monochrome. Version 2 adds colour, fog of war,
and field of view. You own the colour vocabulary.

The engine is built by independent workers who never communicate; a frozen contract defines
every seam. Two other workers are running in parallel on unrelated files.

Your module is **pure data and pure functions, with no `curses` import at all.** That is
deliberate. The terminal side — allocating curses colour pairs, choosing attributes — belongs
to the renderer, which already owns every curses call. You describe *what a thing should look
like*; someone else makes the terminal do it. This is what keeps colour testable headless, and
it is a hard project constraint: every module must be importable and testable without a live
terminal.

Three visibility states drive everything:
- **UNSEEN** — never seen. Not drawn at all; blank space, not a dimmed glyph.
- **EXPLORED** — seen before, not currently in view. Drawn in a darker shade of its natural
  colour, so the player knows the memory is stale.
- **VISIBLE** — currently in the character's field of view. Natural colour.

The target terminal has been probed and confirmed: `COLORS=256`, `COLOR_PAIRS=32767`,
`can_change_color=True`. 256 colours means "darker shade" can be a genuinely different colour
rather than a dim attribute — which looks far better. But the module must **degrade, never
crash**, on an 8-colour or monochrome terminal.

Out of scope, explicitly — do not build, do not stub: monsters, combat, items, inventory,
save-load, multiple levels, stairs, sound. No light sources, no coloured lighting, no per-tile
brightness beyond the three visibility states, no theming system, no user-configurable
palettes, no background colours. Extra surface is a defect here, not initiative.

## Produce

`roguelike/style.py`:
```python
class Visibility(Enum):
    UNSEEN   = auto()
    EXPLORED = auto()
    VISIBLE  = auto()

class Role(Enum):
    TERRAIN = auto()    # wall and floor
    DOOR    = auto()
    PLAYER  = auto()

@dataclass(frozen=True)
class Attr:
    color: int          # 256-colour index; -1 means "terminal default"
    bold: bool = False

def role_for(tile: Tile, is_player: bool = False) -> Role
def attr_for(role: Role, visibility: Visibility, colors: int = 256) -> Attr
```

`tests/test_style.py`.

### The palette — binding

| Role | VISIBLE | EXPLORED |
|---|---|---|
| `TERRAIN` (`#`, `.`) — light gray | **250** | **238** |
| `DOOR` (`+`, `'`) — light brown | **180** | **94** |
| `PLAYER` (`@`) — white, **bold** | **231** + bold | n/a — always visible |

### The capability ladder

| `colors` | TERRAIN / DOOR | EXPLORED |
|---|---|---|
| `>= 256` | the palette above | the palette above |
| `>= 8` | `curses.COLOR_WHITE` / `curses.COLOR_YELLOW` numeric equivalents | same colour as VISIBLE; the dim signal is the renderer's job |
| `< 8` (mono) | `color = -1` (terminal default) | `color = -1` |

You must **not** import `curses` to get `COLOR_WHITE`/`COLOR_YELLOW`. Those are the fixed ANSI
indices 7 and 3; use the integer literals with a comment. Importing curses in a pure data
module would defeat the point of the split.

## Constraints
- Python 3.10+, **standard library only**. `from __future__ import annotations` at the top.
- **Imports only `roguelike.tiles`** from the project, plus stdlib `enum` and `dataclasses`.
  **No `curses` import, at all.** No other project imports.
- `Attr` is `frozen=True`. `Visibility` and `Role` use `auto()` — do not assign explicit values.
- `attr_for(role, Visibility.UNSEEN, ...)` raises **`ValueError`**. Unseen cells are never
  drawn (CONTRACT §4.1), so asking for their attribute is a caller bug and must be loud.
- `attr_for(Role.PLAYER, Visibility.EXPLORED, ...)` — the player is always visible, so this is
  also a caller bug. Raise `ValueError`.
- `role_for` maps `Tile.WALL` and `Tile.FLOOR` to `Role.TERRAIN`, `Tile.DOOR` to `Role.DOOR`,
  and returns `Role.PLAYER` whenever `is_player` is True regardless of the tile — the player is
  drawn over whatever they stand on, including a wall.
- Pure: no module-level mutable state, no caching, no I/O, no randomness. `attr_for` with the
  same arguments returns an equal `Attr` every time.
- Capability is a **parameter** (`colors`), never detected inside this module — detection needs
  curses and belongs to the renderer. Default `256`.
- Do not add background colours, a `theme` parameter, an `Attr.dim` field, or any name not
  listed above. The `EXPLORED` dim signal on sub-256 terminals is carried by the renderer, not
  by you.
- Tests must not initialise curses and must pass with no TTY. No `conftest.py`.

## Acceptance criteria
- `Visibility` has exactly `UNSEEN`, `EXPLORED`, `VISIBLE`; `Role` has exactly `TERRAIN`,
  `DOOR`, `PLAYER`. No extra members.
- `role_for(Tile.WALL)` and `role_for(Tile.FLOOR)` are `Role.TERRAIN`;
  `role_for(Tile.DOOR)` is `Role.DOOR`.
- `role_for(tile, is_player=True)` is `Role.PLAYER` for **every** tile including `Tile.WALL`.
- At `colors=256`: `attr_for(TERRAIN, VISIBLE).color == 250`;
  `attr_for(TERRAIN, EXPLORED).color == 238`; `attr_for(DOOR, VISIBLE).color == 180`;
  `attr_for(DOOR, EXPLORED).color == 94`; `attr_for(PLAYER, VISIBLE) == Attr(231, bold=True)`.
- The player is the only role with `bold=True`; every other returned `Attr` has `bold=False`.
- **Every EXPLORED colour is darker than its VISIBLE counterpart** at 256 colours — assert
  `attr_for(r, EXPLORED).color < attr_for(r, VISIBLE).color` for `TERRAIN` and `DOOR`, with a
  comment that this holds because both pairs sit on the xterm grayscale/brown ramps where a
  lower index is darker. This is the rule the user actually asked for, so test it directly.
- `attr_for(..., Visibility.UNSEEN)` raises `ValueError` for all three roles.
- `attr_for(Role.PLAYER, Visibility.EXPLORED)` raises `ValueError`.
- At `colors=8`: no returned `color` exceeds 7, and none raises. `TERRAIN` and `DOOR` get
  distinguishable colours (assert they differ).
- At `colors=2` and `colors=0`: every returned `Attr` has `color == -1` and nothing raises.
- `colors` values of 256, 88, 16, 8, 2, 0 all produce a valid `Attr` for every
  `(role, visibility)` pair that does not raise — a full cross-product sweep, asserting no
  exception and `isinstance(a.color, int)`.
- `Attr` is frozen: assigning to `.color` raises `dataclasses.FrozenInstanceError`.
- `Attr` equality is by value: `Attr(250) == Attr(250)` and `Attr(250).bold is False`.
- Purity: `attr_for` called twice with the same arguments returns equal values.
- `style.py` imports **no `curses`** and nothing from the project except `roguelike.tiles` —
  assert by parsing the module source with `ast`.
- Importing `roguelike.style` in a fresh subprocess with stdin from `/dev/null` succeeds and
  does not initialise a terminal.
