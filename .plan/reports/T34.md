## Import purity — the load-bearing constraint

`loot.py` imports only `roguelike.items` and `roguelike.level`, and nothing else —
verified by `test_loot_imports_only_items_and_level` (asserts the *exact* set) and
`test_loot_does_not_import_the_forbidden_modules` (explicit negative check on `game`,
`npc`, `combat`, `render`, `world`, `tiles`, `curses`). No `random.Random` is created here;
`random` is imported only under `TYPE_CHECKING`.

**The interesting problem this constraint creates, and how it's solved:** "passable with
no door open" (§27.2) is exactly what `world.is_passable(level, frozenset(), x, y)`
computes — but `loot.py` cannot import `world.py` (only `items` and `level` are permitted),
and cannot import `tiles.py` either, so it cannot compare a tile against `Tile.DOOR`
directly.

It doesn't need to. The generator's own guarantees make `Level.rooms` sufficient:

- G7 carves every cell of a room's floor rectangle (`Room.contains`) to `FLOOR` or a stair
  — **never** a door.
- G9a-G9d place every door on some room's wall ring (`Room.on_perimeter`), and G5 makes
  every two rooms' floor-plus-ring boxes pairwise disjoint.
- A corridor cell is, by construction, outside every room's ring box, and is always plain
  `FLOOR` — never a door.

So the only *walkable* cells that ever satisfy `room.on_perimeter(x, y)` for some room are
doors (the rest of a wall ring is `WALL`, which is never walkable). That makes

```python
level.is_walkable(x, y) and not any(room.on_perimeter(x, y) for room in level.rooms)
```

exactly "passable, no door open" — with zero `Tile` dependency. I verified this
mechanically, not just by proof: `is_walkable(x,y) and any(room.on_perimeter(x,y) ...)`
was checked against `level.tile_at(x, y) is Tile.DOOR` for every walkable cell on 200
generated levels (123,000 cells) — zero mismatches. Full reasoning is in `loot.py`'s
module docstring ("Detecting a door without importing `Tile`").

This does mean `place_chest` trusts `Level.rooms` to agree with the grid, which only holds
for levels built by `generate_level` (which enforces it as G5/G7/G9a-G9d on every level it
returns). A hand-built `Level` with mismatched `rooms` is outside that contract — the same
position any other consumer of `Level.rooms` is in.

## The depth/grade table — asserted literally, per row

Four `@pytest.mark.parametrize` tests, one per row of §27.1, each checking every depth in
that row's range against the exact tuple. Plus: every row's three weights sum to 100 for
depths 1-39; `grade_weights(1)[2] == 1` (the "extremely low chance of a higher grade"
requirement, asserted as such); and the `fine` share is monotonically non-decreasing across
depths 1-39.

`chest_chance`: 12 for every depth 1-9, 8 for every depth in {10, 11, 15, 30, 100}; never
raises for depth in `range(1, 500)`.

## Placement — measured, not just asserted correct

`place_chest` over a 190-run sweep (150 seeds at the default 80x22 with depth cycling
1-20, plus 20 seeds each on two other sizes) placed at least a handful of real chests
(sweep constant, so this is a fixed lower bound, not flaky). Every placed chest: sits on a
walkable, non-door cell (checked directly against `Tile.DOOR`, importable from the *test*
file even though not from `loot.py`); is >= `CHEST_SAFE_RADIUS` (8) Chebyshev from
`player_start`; holds 1-3 items; every item is one of `items.py`'s eleven module
constants (`ALL_ITEM_CONSTANTS`, checked by equality).

### Measured grade distribution at depths 1, 5, 12

6000 seeds per depth on one small (30x18, `max_rooms=5`) generated level, restricted to the
weapon/shield items in the chests found (consumables have no grade and are excluded from
the tally — see below):

| depth | expected (crude/std/fine) | observed | graded items sampled |
|---|---|---|---|
| 1 | 80 / 19 / 1 | 78 / 19 / 1 | 903 |
| 5 | 55 / 40 / 5 | 56 / 38 / 5 | 903 |
| 12 | 15 / 70 / 15 | 14 / 69 / 16 | 629 |

The shipped test uses an 18-point band (not this tight — that number is a one-off sanity
run, not the test's tolerance) specifically so it never gets flaky; the actual numbers
above show the roll is exactly on target.

## Determinism

- Same seed, same level, same depth -> identical `Chest` (including `None`), checked over
  300 seeds on one generated level.
- Different seeds generally differ (200 seeds -> more than one distinct outcome).
- **`PYTHONHASHSEED` independence**, via `subprocess`: 30 seeds x 3 depths, two different
  hash seeds, byte-identical stdout. No `place_chest` internal ever iterates a `set` or
  `dict` in a way that reaches the output — `_POOLS` is a `dict` keyed by `Grade`, but it
  is only ever indexed by a known key, never iterated.

## No legal cell

Three shapes, all returning `None` promptly with a wall-clock guard (`time.perf_counter()`,
< 1.0s): a 6x6 generated level (the generator's floor size — its longest Chebyshev span is
under the 8-cell radius), a single-cell hand level, and an all-wall hand level. A fourth
test (`test_the_safe_radius_is_never_relaxed_to_force_a_placement`) uses a 10x10 open room
with the player centred, so every cell is inside the radius by construction, and checks 100
seeds all come back `None` — the radius is never relaxed to manufacture a chest.

## Assumptions — where §27 is silent

1. **Consumables and grade.** `Consumable` has no `grade` field (§25), so `grade_weights`'
   three bands can only directly govern which *weapon/shield tier* is drawn. Since chests
   are stated to be the only source of any item at all, excluding
   `POTION_OF_HEALING`/`BANDAGE` from loot entirely would make them unobtainable in the
   whole game. **Resolution:** every grade's concrete item pool is that grade's graded
   weapons and shields, plus both consumables, always — so a consumable is reachable at
   every depth and every grade roll, and the rolled grade only ever selects among
   equipment. This is why the grade-distribution measurement above counts weapon/shield
   draws only: a consumable draw carries no grade signal to check.
2. **Item count per chest.** §27.2 says "1-3 items" without naming a distribution. I drew
   `rng.randint(1, 3)` — uniform, the simplest reading, and not tested for a shape beyond
   "always 1-3" since the contract states no target shape.
3. **"Not on a cell holding a monster" (contract §27.2) vs. the T34 brief.** The
   contract's placement bullets include "not on a cell holding a monster"; the brief's own
   restated placement rules (and the binding `place_chest(rng, level, depth)` signature,
   both in §27's code block and the brief's "Produce" line) do not give this function any
   way to know where monsters are — there is no `occupied`/`npcs` parameter, and `loot.py`
   must not import `npc.py`. I followed the brief and the signature literally and did not
   implement monster-avoidance; it isn't testable from inside this module. **Flagging for
   the orchestrator, not stopping on it:** if a chest and a monster ever need to be kept
   off the same cell, that ordering has to happen in `game.py`, which sees both
   `spawn_npcs`' output and `place_chest`'s output before committing either to
   `LevelState`.
