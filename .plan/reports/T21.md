Contract deviations: none. Four judgement calls the contract leaves open, all recorded here
rather than made silently:

1. **`AUTO_EXPLORE` with nothing left to explore reports on the first `advance`, not inside
   `step`.** §7.4's `AUTO_EXPLORE` row is unconditional ("start `Activity(AUTO_EXPLORE)`, no
   turn") — unlike the `DESCEND` row, which the contract explicitly splits in two — so `step`
   starts the activity unconditionally and the first `advance` finds no frontier, clears it and
   emits `EXPLORED_EVERYTHING`. §11's row ("immediate `EXPLORED_EVERYTHING`, no turn") is
   satisfied observably: no turn is consumed on either call, and the message is on screen after
   one 100 ms tick. Special-casing it in `step` would have duplicated the frontier computation
   in a second place. Pinned by
   `test_auto_explore_with_nothing_left_reports_it_and_costs_no_turn`.
2. **`AUTO_WALK` plans over the whole level's planning-passability; `TRAVEL` and `AUTO_EXPLORE`
   are restricted to `explored`.** §7.5 states the explored restriction for `TRAVEL` only, and
   §19.1's no-cheating rule is scoped to `frontier_cells`. `walk_step` is a purely local rule
   that reads at most the cells touching the one under consideration — all of which are within
   sight — so restricting it would change nothing except to make "stop before the opening"
   depend on how much of the room ahead happened to be mapped, which is exactly the acceptance
   criterion that must be reliable. The two functions are `_whole_level_passable` and
   `_explored_passable`, named apart so the difference cannot be reached for by accident.
3. **"Nearest" staircase means nearest by route.** `_travel_or_report` hands *all* the explored
   staircases of that kind to `find_path` at once and takes the one it reaches first, so a near
   but walled-off staircase never beats a reachable one. The octile fallback fires only when
   every known staircase is unreachable through explored ground — a case that cannot arise on
   today's fully-connected generator, and where `advance` answers `NOTHING_FURTHER` whichever
   goal was named. Pinned by `test_travel_picks_the_nearest_of_several_known_staircases`.
4. **`_ACTIVITY_BLOCKED` is a defensive table.** Every cell a planner proposes is
   planning-passable, and the only planning-passable cell `try_move` refuses is a closed door,
   which is bumped open instead — so the "blocked by something other than a door" arm of
   `advance` is unreachable today. It answers with the same event the same activity gives when
   it runs out of route, rather than raising.

Assumptions made:
- **`interruption` is called after the move, not on the finishing paths.** §7.5's order is
  "perform the move … then call `interruption(before, after)`", and §7.6 says it is called
  "after every activity turn". A turn only happens when a move or a door bump happened, so the
  call sits there. It returns `None` today in every case, so nothing observable turns on it;
  `test_advance_calls_interruption_after_every_activity_turn` asserts the call site by AST so it
  cannot be quietly dropped.
- **`came_from` is advanced only for `AUTO_WALK`, and only when the player actually moved.** A
  door bump does not move you, so it must not disturb `came_from` or the walk would forget which
  way it came the moment it opened a door. `TRAVEL`/`AUTO_EXPLORE` leave the field alone, since
  §19 documents it as `AUTO_WALK`'s.
- **`advance` also returns the state unchanged when `running` is `False`.** Not required — a
  stopped game never has an activity, because every command clears one — but a stopped state
  must stay inert whatever it is handed.
- **`_cancelled` is a private function rather than inline code in `run`.** Building an `Event`
  and clearing a field is a rule, and §7.7 requires `run` to hold none. It is deliberately not
  reachable through `step`, because the whole point is that the cancelling key never becomes a
  command.
