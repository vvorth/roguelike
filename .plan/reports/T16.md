Assumptions made:
- §4.2's composition formula (`len(message) + 1 + len(status_right) <= width`) reserves one
  separator column unconditionally, even when `status_right == ""`. Applied literally: a
  message that exactly fills `width` with an empty `status_right` loses its last character to
  that reserved column (e.g. width 10, message `"exactly10!"` → `"exactly10 "`, not
  `"exactly10!"` as under the old v2 status-line rule). Pinned by
  `test_message_only_status_line_is_padded_or_truncated_to_width`. In practice this never bites
  during real play: `format_status_right` (§7.2, owned by T17) always returns a non-empty
  `"Level {depth}  Seed {master_seed}"`, so `status_right` is never actually empty at runtime —
  flagging this only because it's a genuine, testable behavioural divergence from v2's bare
  status-line truncation and a worker relying on the old semantics for an empty-status_right
  case would be surprised.
- Stair glyphs needed zero new logic in `render_to_cells`: the existing per-cell branch already
  does `char = TILE_CHARS[tile]` for any non-door tile, and `TILE_CHARS` (frozen by T13) already
  maps `STAIRS_UP`/`STAIRS_DOWN` to `<`/`>`. Added tests to pin this rather than any code change.
- Used `level.in_bounds` (pre-existing, from T13's `level.py`) unchanged for the player
  out-of-bounds check, exactly as v2 did.
- Test helper `render()` (existing convenience wrapper predating this task) now maps its
  `status=` kwarg onto `Chrome(message=status)` — kept for minimal diff on the many call sites
  that only ever cared about one text field; call sites that needed `stats`/`status_right` too
  construct `Chrome(...)` directly.
