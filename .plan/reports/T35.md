## THE PUBLIC SURFACE — the next worker wires this up

### `render_to_cells`'s exact final signature

```python
def render_to_cells(
    level: Level,
    player_pos: tuple[int, int],
    visible: frozenset[tuple[int, int]],
    explored: frozenset[tuple[int, int]],
    open_doors: frozenset[tuple[int, int]],
    chrome: Chrome,
    npcs: tuple[NpcGlyph, ...] = (),
    target: tuple[int, int] | None = None,
    projectile: tuple[int, int] | None = None,
    chests: frozenset[tuple[int, int]] = frozenset(),
) -> list[list[Cell]]:
```

Only `chests` is new, appended last with a default of `frozenset()` — every pre-v6 call site
(positional or keyword, up through `projectile`) keeps working unchanged; this is asserted by
`test_render_to_cells_defaults_to_no_chests`.

**`chests` is a plain `frozenset[tuple[int, int]]` of positions — not a dataclass.** Unlike
`NpcGlyph`, a chest carries no per-instance data this module needs (no species-equivalent,
no variable glyph): every chest draws identically, so there is nothing to wrap. The brief's
"exactly as NPC glyphs do" is about *how* the data arrives — as a parameter, never derived
from an import this module cannot make — not about the shape of the parameter itself.
`open_doors` was already the established precedent for "a frozenset of positions" on this
signature, so `chests` follows it rather than inventing a new pattern.

### Glyph and colour

- **Glyph: `CHEST_CHAR = "~"`** (the brief's own proposal), a new public constant in
  `render.py`, exported in `__all__` right after `PROJECTILE_CHAR` — it is the renderer's own
  invented symbol, not tile data, exactly like the projectile glyph. Collision-checked
  explicitly against `{"#", ".", "+", "'", "<", ">", "@", "*", "r", "j", "B", "s"}` in
  `test_chest_glyph_does_not_collide_with_any_forbidden_glyph`.
- **Colour: `Role.CHEST` — 256-colour `220` (visible) / `178` (explored)**, both on the xterm
  256-colour gold ramp (220 = gold1, 178 = darkgoldenrod3), distinct from every other role's
  colour (terrain 250/238, door 180/94, player 231, projectile 226, the four species
  250/173/140/70) — asserted in one set-disjointness test. 8-colour fallback is `_ANSI_YELLOW`
  (matching the door's fallback, same as every other non-terrain non-NPC role at 8 colours);
  monochrome is `-1` (terminal default), matching every other role. Not bold — only the player
  is bold.

## The one decision that was mine: chests are drawn from `explored`

**Chosen: yes, a chest is drawn from `explored`, exactly like terrain — the brief's own
recommendation, and I agree with the reasoning as given.** A monster is never drawn from
`explored` because CONTRACT-v5 §4/§15 v5's entire premise is that a monster *moves*, so a
remembered position is stale information dressed up as current information — drawing it would
be drawing a lie the player would act on. A chest has no analogous behaviour: nothing in §27
moves it, removes it, or relocates it once `place_chest` sets its position; the only thing that
changes about a chest over its lifetime is `opened`, which is a content change, not a position
change. Drawing it from `explored` is therefore not "drawing stale data" the way an NPC would be
— it's the same category of fact as "there is a wall here," which is exactly what `explored`
already exists to remember. The alternative (treating a chest like an NPC, hiding it the instant
it leaves `visible`) would make the fog-of-war memory system actively worse than useless for
chests: the player would see one, walk away to fight something, and have the game pretend it
never saw it — punishing exactly the exploration behaviour fog of war is supposed to reward.

Implemented identically to how terrain visibility is resolved: `visible` wins over `explored`
wins over "not drawn at all" (never leaking map shape through unseen area, same discipline as
everywhere else in this module). Pinned by
`test_chest_is_drawn_from_explored_because_it_does_not_move` (named after the reasoning, per
the acceptance criteria), plus `test_visible_chest_is_drawn_with_its_glyph_and_role`,
`test_chest_visible_wins_over_explored_when_in_both`, and
`test_chest_on_unseen_cell_is_not_drawn_and_reveals_no_terrain`.

**Draw order, and why:** terrain → chests → NPCs → player → projectile → target highlight.
Chests are drawn right after terrain (so they can be remembered like it) but *before* NPCs and
the player, so both still win on a shared cell — asserted directly by
`test_npc_wins_over_chest_on_the_same_cell` and `test_player_wins_over_chest_on_the_same_cell`,
satisfying the acceptance criterion "the player and monsters still win over a chest on the same
cell" for both halves.
