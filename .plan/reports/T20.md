Assumptions made:

1. **`walk_step` with `came_from is None` in a corridor steps to `position + direction`**, and
   therefore never reports `"intersection"` on the first step. CONTRACT-v4 §19.2 states the
   corridor rule in terms of "candidates excluding `came_from`", which excludes nothing when
   `came_from is None`, and then resolves it with "the first step of a walk has `came_from is
   None` and **uses `direction`**; subsequent steps in a corridor follow the corridor and **may
   turn**". I read that contrast literally: the first step obeys the key just pressed, and only
   later steps — where `direction` is stale — hand the decision to the corridor. The visible
   consequence is that `w`+direction pressed while standing *on* a junction walks out of it the
   way it was told to, rather than refusing to move at all. Tested explicitly
   (`test_the_first_step_out_of_a_junction_obeys_the_key_that_was_pressed`).
2. **`direction == (0, 0)` stops with `"blocked"` in a corridor too**, not only in the open.
   CONTRACT-v4 §11 specifies only the open case. In a corridor the alternative is to "move" onto
   the cell already occupied, which would burn a turn going nowhere for ever. Consistent with
   `movement.try_move`, which already treats a zero delta as `moved=False`.
3. **The "stop before a room" (`"opening"`) rule applies to the corridor branch only.** In the
   open, the next cell is almost always itself wide, so applying it there would stop every walk
   after zero steps. This matches the brief's acceptance criterion for the open case ("walks
   straight in `direction`, ignoring side openings, until `(None, "blocked")`"). Stepping from
   the open *into* a corridor mouth is an ordinary move, and is tested.
4. **Out-of-bounds members of `explored` are skipped rather than raising.** Nothing produces
   them today (`fov.compute_visible` returns in-bounds cells only); this keeps `frontier_cells`
   to the "never raises" convention of §11.

### How the no-cheating claim is proved, not asserted

Three independent tests, and I verified each one **fails** against a deliberately cheating
implementation (one that asks whether the unexplored neighbour is walkable terrain):

- `test_frontier_cells_returns_the_same_set_for_two_levels_that_differ_only_unexplored` — the
  test the brief specifies. Two levels identical in columns 0–3 and different beyond; explored
  is exactly columns 0–3. Run both with the door closed *and* with it open, so the answer rests
  on the unexplored-neighbour clause alone rather than on the closed-door shortcut. A separate
  test guards that the twins really are identical inside and different outside.
- `test_frontier_cells_never_asks_what_an_unexplored_cell_contains_hand_built` /
  `..._generated` — a duck-typed stand-in for `Level` that **raises** the instant anything asks
  for the tile of an unexplored cell. It overrides `is_walkable` as well as `tile_at`, because
  the real `Level.is_walkable` reaches its own `tile_at` internally and would otherwise slip
  past the check. Each of these also asserts that the frontier genuinely borders unexplored
  *floor*, so the test cannot pass because the peek path was never reached — an earlier version
  of the generated case did exactly that and was strengthened.

I also confirmed the suite catches both documented silent failure modes:
- Planning with `is_passable` instead of `is_planning_passable` collapses coverage to **8–18%
  with 0 turns taken** — auto-explore stalling in the first room, caught loudly by the
  end-to-end test.
- Dropping the closed-door frontier clause is caught by
  `test_a_closed_door_is_a_frontier_even_when_everything_around_it_is_explored`.

Open questions for integrator:

1. **`advance` must drop the character's own cell from the frontier goal set.** If the character
   stands on a frontier cell, `find_path` returns `[start]` (§18.1), there is no `path[1]`, and
   the activity makes no progress — a silent stall rather than an error. My end-to-end driver
   does `goals = frontier_cells(...) - {player}`. Instrumented over five full runs, the
   character never actually stood on a frontier at the default radius 20 (all eight neighbours
   are always seen), so this is a cheap guard against a case that does not arise today rather
   than a live bug. **No path → `EXPLORED_EVERYTHING`** per §7.5 covers the case where that
   subtraction empties the goal set.
2. **`.plan/reports/T19.md` does not exist.** `roguelike/pathfind.py` and
   `tests/test_pathfind.py` are present and complete, and I built against them directly; the
   two facts about them quoted in my brief (`find_path` never calls `passable` on `start`; the
   multi-goal heuristic is `min(octile(node, g) for g in goals)`, so cost scales with
   `|goals|`) both hold on inspection. Flagging only in case the orchestrator expected the file.
3. **The closed-door frontier clause does not move the coverage number on today's generator**,
   and that is not a defect. While anything beyond a closed door is unseen, the door already
   qualifies via its unexplored neighbours; the clause bites only when a door is ringed entirely
   by already-mapped cells, where opening it reveals nothing new. Its live effect is therefore
   that auto-explore *opens* such doors before declaring the level finished — a few extra turns,
   and `EXPLORED_EVERYTHING` arriving slightly later than a reader of the coverage table might
   expect. The contract requires the clause and it is implemented and unit-tested.
4. **Frontier goal sets are large** — a few hundred cells on a fresh 80×22 level — and §18's
   heuristic is recomputed per node against every goal. Measured worst case is 2.6 ms per turn,
   comfortably inside budget, so no action is needed; noting it only because the cost scales
   with `|goals|` if the map size ever grows.
5. `walk_step` returns `""` while moving, so `if reason:` is the test for "the walk stopped".
   `next_coord is None` and `reason != ""` are equivalent — asserted exhaustively over a swept
   map, so T21 may rely on either.
