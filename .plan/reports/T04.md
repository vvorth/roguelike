Assumptions made:
- `_KEY_BINDINGS` is built once at import time by a helper; the brief asked for a single
  module-level mapping table rather than an if/elif chain, and the table is kept private so
  the module's public surface stays exactly what §5 lists. `tests/test_keys.py` reads
  `keys._KEY_BINDINGS` for the exhaustiveness/invariant tests — the only intra-project use of
  a private name, and it is by the owning task's own test file.
- Type check order in `translate_key`: `str` first, then `int`. Because `bool` is an `int`
  subclass, `True`/`False` are accepted and normalise to key codes 1/0, both unbound, so they
  return `UNKNOWN_COMMAND` rather than raising — the brief explicitly says `bool` need not be
  special-cased here. (This differs from `generate_level`'s `bool`-rejects rule in §3.1, which
  is not my module.)
- A length-1 `str` outside ASCII (e.g. `'é'`) is converted with `ord()` like any other and
  falls through to `UNKNOWN_COMMAND`; only a non-`int`/non-`str` type or a `str` of length
  != 1 raises `TypeError`.
- `int` subclasses other than `bool` (e.g. `IntEnum`) are normalised with `int()` before
  lookup, so they hash to the same key as the plain int.
- Tests import `curses` solely for its `KEY_*` constants and assert structural properties by
  parsing `roguelike/keys.py` with `ast` (no `roguelike` import, stdlib-only imports,

  One test spawns a subprocess with `stdin=DEVNULL` to confirm a fresh-process import of
