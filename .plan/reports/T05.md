Assumptions made:
- **Zero delta is an explicit branch, checked before walkability.** CONTRACT §6 states two
  rules that overlap: "if `level.is_walkable(*target)` → `MoveResult(target, True)`" and
  "`dx == 0 and dy == 0` → `MoveResult(position, False)`". When the player stands on FLOOR,
  the target of a zero delta *is* the current cell and *is* walkable, so the first rule alone
  would return `moved=True`. I read the zero-delta rule as the more specific one and made it
  win: `try_move(level, pos, 0, 0)` returns `moved=False` unconditionally, walkable cell or
  not. This is the only reading consistent with the acceptance criterion
  ("`try_move(level, pos, 0, 0)` returns `moved=False`") and with BRIEF Q8 (there is no wait
  action, so a no-op must not consume a turn). Flagging it because it is the one place where
  a literal top-to-bottom transcription of §6 gives the wrong answer.
- **Delta validation happens before anything else**, so `try_move(level, pos, 2, 0)` raises
  `ValueError` regardless of what is at the target. §6 does not order the two rules; raising
  first is the only way "movement is single-step only" is enforceable.
- **Membership test, not range arithmetic**, for the delta guard: `dx not in (-1, 0, 1)`.
  Consequence: `True`/`False` pass the guard (`True == 1`), since §6 and §11 mandate
  `ValueError` only for values *outside* `{-1, 0, 1}` and mandate no `TypeError` anywhere for
  `try_move`. I added no type checks rather than invent an unspecified error. A non-numeric
  `dx` raises `ValueError` from the guard, not `TypeError`. Per §5, `keys.translate_key`
  only ever produces `dx, dy ∈ {-1, 0, 1}`, so the real caller never exercises this.
- **On rejection I return the caller's tuple object itself**, not a copy — §6 says the
  position is "unchanged and identical" to the input. Tested with `is`, not just `==`. On
  acceptance a fresh tuple is built, so the input tuple is never aliased into the result.
- `position` is only ever indexed (`position[0]`, `position[1]`), never unpacked with a
  length check, so a malformed `position` raises whatever indexing raises. §6 specifies no
  behaviour here; I chose literal fidelity over inventing a rule. (Same choice T01 recorded
  for `player_start`.)
- Rejection goes through `level.is_walkable` exclusively. `level.tile_at` is never called and
  no bounds check is re-derived, so walls, the border, and off-map coordinates share one code
  path by construction rather than by discipline.

Open questions for integrator:
1. The zero-delta precedence noted under Assumptions is the one genuine ambiguity in §6, and
   it matters to T06: if `game.step` ever forwards a `(0, 0)` MOVE command, my `moved=False`
   guarantees no turn is consumed. Per §5 that command cannot exist (a `MOVE` never carries
   `(0, 0)`, and numpad `5` is `UNKNOWN`), so the two layers agree — but they agree by
   redundancy, not by one relying on the other.
2. `try_move` does not require the *starting* position to be in bounds or walkable — it only
   tests the destination. A player somehow standing on a wall or off-map can therefore step
   onto any adjacent walkable cell. This falls out of the single-predicate design and is
   tested as such; it is also the behaviour that keeps §7's `render_to_lines` contract
   ("the player is drawn even if standing on a wall") coherent. If the integrator wants a
   start-position precondition, that is a contract change, not a code change.
3. `MoveResult` carries no reason for rejection, by explicit instruction. A caller that wants
   to distinguish "wall" from "off-map" for a status message must ask `level.in_bounds`
   itself; §7's `format_status` does not, so nothing currently needs this.
