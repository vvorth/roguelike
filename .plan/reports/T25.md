`combat.py` imports only `roguelike.stats` (specifically `Actor` and `derive`) — `items` and
`status` are not imported because `resolve_attack`'s body never needs `Weapon`/`WeaponKind` or
`StatusEffect`/`apply_effect` directly; the contract's import list is a ceiling ("imports only
`stats`, `items`, `status`"), not a mandate to import all three, and `tests/test_combat.py`
asserts this graph via `ast` (`test_combat_module_imports_only_the_allowed_modules`).

Contract deviations: none. Both binding formulas (§23.1 to-hit, §23.2 damage), the poison rule
(§23.3), the death rule (§23.4), the roll order, and every "Do not add" item in the brief were
followed exactly. Neither of the two traps (attacker accuracy term; STR on natural attacks) was
reintroduced — each has a dedicated, named regression test.

Assumptions made:
- **Import set is a subset, not an exact match.** As above — read the contract's "Imports
  `roguelike.stats`, `roguelike.items`, `roguelike.status`" as the allowed set, verified by
  testing that every import found by `ast` is a member of that set (plus `__future__` and
  `dataclasses`), not that all three must appear.
- **`defender.status_effects` is read nowhere.** Nothing in §23's formulas references status
  effects on either actor (poison is an *output* of this call, not an input), so `Actor.status_effects`
  is simply unused by `combat.py`; a test (`test_resolve_attack_does_not_mutate_defender_status_effects`)
  confirms it is also never touched.
- **`derive` is called once per `resolve_attack` invocation, on the defender only.** The attacker's
  `Derived` (speed, evasion) is never computed — only `attacker.stats.str_` is read, directly,
  since STR modifier math needs the primary stat, not a derived one.

Exact `rng` draw order (binding, per the brief — restated here for the integrator building the
caller in `game.py`):
1. **to-hit roll** — `rng.randint(1, 100)`, always, exactly once.
2. **damage roll** — `rng.randint(damage_min, damage_max)`, only if the to-hit roll succeeded.
3. **poison roll** — `rng.randint(1, 100)`, only if the attack hit **and** `poison_chance > 0`.

So a miss consumes exactly 1 draw; a hit with `poison_chance == 0` consumes exactly 2; a hit
with `poison_chance > 0` consumes exactly 3. All three counts are asserted directly with a
counting `Random` subclass (`test_miss_consumes_exactly_one_draw`,
`test_hit_without_poison_consumes_exactly_two_draws`,
`test_hit_with_poison_chance_consumes_exactly_three_draws`), and the miss case is cross-checked
a second way by comparing `Random.getstate()` against a hand-rolled single draw
(`test_miss_consumes_one_draw_by_comparing_generator_state`).

Observed statistics from the test run (fixed seed sequences `range(N)`, so fully reproducible):
- **Hit rate** at baseline vs baseline (defender evasion 5, chance 85%): **86.05%** over 2000
  seeds — inside the required 80–90% band
  (`test_statistical_hit_rate_near_85_percent_at_baseline_over_2000_seeds`).
- **Poison rate** at `poison_chance=30`, measured as poisoned/hits against a low-evasion
  defender (evasion 0, chance 90%) over 3000 seeds: 2698 hits, 792 poisoned = **29.36%** —
  inside the required 20–40% band
  (`test_poison_rate_is_roughly_30_percent_of_hits_at_poison_chance_30`). Note this is the rate
  *conditional on a hit*, since the poison roll is only drawn on a hit; the brief's wording
  ("set roughly 30% of the time") is read that way because an unconditioned rate would
  necessarily track the hit rate too and conflate two independent probabilities.

Open questions for integrator:

1. **None on the formulas.** Every acceptance criterion in the brief has a corresponding, named
   test: the attacker-accuracy-term trap
   (`test_to_hit_is_independent_of_attacker_agi_not_a_reintroduced_accuracy_term`) and the
   natural-attack STR double-penalty trap (`test_rat_bite_is_not_double_penalised_by_str_full_range_appears`)
   are each isolated and named after the bug they guard against, per the brief's instruction.
2. **Ranged-weapon `strength_applies=False` is the caller's responsibility, not enforced here.**
   `resolve_attack` has no way to know a weapon is ranged (it never sees a `Weapon`) — the
   caller (presumably `game.py`, T28) must pass `strength_applies=False` for `SHORTBOW` and
   `True` for `DAGGER`. Flagging this explicitly since it's the one asymmetry a careless call
   site could get backwards with no error raised — `resolve_attack` will happily compute a
   plausible-looking (wrong) result either way.
3. **`AttackResult` carries no identity for which actor is attacker/defender.** Confirmed
   deliberate per the brief's "Out of scope" list (no `events` list, no message generation) —
   the caller already knows both `Actor` values it passed in, so this isn't a gap, just noting
   it for whoever writes the `game.py` call site.
