Assumptions made:
- **"On a staircase" is decided by coordinate, not by tile.** §10 v3 forbids `game.py` from
  importing `roguelike.tiles`, so `step` cannot ask what tile the player stands on. `DESCEND`
  tests `player == level.stairs_down[0]`, `ASCEND` tests `player == level.stairs_up`, and the
  `STAIRS_HERE_*` events come from the same comparison. G18 makes the two readings identical on
  any generated level (exactly one `STAIRS_UP` cell, at `stairs_up`; one `STAIRS_DOWN`, at
  `stairs_down[0]`). A hand-built level with no stairs has `stairs_up is None`, which no
  coordinate equals, so it simply never produces stair events.
- **`outcome` is filled from the message table, inside `step`.** §7.1 requires `step` to set
  `outcome` on leaving the dungeon, and §7.2 forbids `game.py` from formatting wording. The only
  way to satisfy both is `outcome = events.message_for((Event(LEFT_DUNGEON),))`. This is the one
  `message_for` call outside `run`; `game.py` still contains no sentence, pinned by a test that
  walks the AST and asserts no non-docstring string literal is a sentence or contains a
  `MESSAGES` value.
- **An accepted move onto ordinary ground replaces `events` with `()`.** The event rule says the
  tuple is replaced whenever a turn is consumed; a plain step consumes one and produces nothing,
  so the previous message is cleared. That is what makes "the message stays until another turn"
  literally true.
- **The current depth is never a key of `saved`.** On arriving at depth *d*, `d` is popped from
  the freshly built dict, so `state.depth not in state.saved` always holds and `explored` /
  `open_doors` on the state are the single live copy of the current level. The contract says
  `saved` holds levels "the player has left"; it does not say what to do with a stale entry for
  the level being re-entered, and leaving one in would be a second source of truth. Pinned by
  `test_the_current_depth_is_never_a_key_of_saved`.
- **`ASCEND` at depth > 1 with no `saved[depth-1]` raises `KeyError`.** The contract states the
  entry always exists ("you can only be at depth *d* by having descended through *d-1*"), so
  this is only reachable by hand-constructing an impossible state. I left it as an unguarded
  lookup rather than inventing an error path the contract does not describe. Not tested — a test
  would be pinning undefined behaviour.
- **`level_for` does not re-validate `required_up`'s range.** T15 suggested an assertion. The
  generator already raises `ValueError` with an "anchorable" message for an out-of-range
  coordinate, so the failure is loud, not silent, and duplicating the range check in `dungeon.py`
  would be reimplementing validation another module owns. Documented in the docstring and pinned
  by `test_a_coordinate_from_a_differently_sized_map_is_rejected_not_silently_moved`, which
  proves the honest-chain case can never trip it (`test_a_deep_chain_never_trips_the_anchorable_range`,
  12 depths).
- **`new_game` places the player via `level.player_start`**, which G17 pins to `stairs_up`.
  Tests assert `state.player == state.level.stairs_up` and that the tile there is
  `Tile.STAIRS_UP`, so the contract's wording is what is checked, not the field I read.
- **`max_rooms` is left at the generator's default in `level_for`**, and descent reuses the
  *current* level's `width`/`height` for the level below — so a dungeon is a chain of
  same-sized levels, which is also what keeps every descent coordinate anchorable.
- Hand-built test levels derive their stair fields from the map glyphs (`<`, `>`), so they are
  stair-consistent the way a generated level is. Descent tests that must really *generate* use a
  20x7 hand-built level (the generator needs `MIN_ROOM_SIZE + 2 == 6` on each axis); the
  multi-level tests use real generated dungeons at 40x18 for speed.
- One test drives `run` with a **stub screen object** (`StubScreen`) — not a terminal, no curses
  initialised, no TTY. The brief forbids testing `run`/`play` against a *real* terminal; a stub
  costs nothing and is the only thing that can catch a `render_to_cells` signature mismatch,
  which is precisely the break T16 flagged. `play` is not executed at all; it is covered by AST
  hygiene tests only.

Open questions for integrator:

1. **`main.py` and `tests/test_integration.py` need the new signatures.** `play(seed, width,
   height)` is unchanged, so `main.py` may already be fine — but `new_game` takes a **master
   seed**, not a `Level`; `run(stdscr, state)` takes a `GameState`, not a `Level`, and now
   **returns** one; `format_status` no longer exists (use `format_stats` +
   `format_status_right`); and `render_to_cells` takes a `render.Chrome`, not a string.
   `tests/test_integration.py` currently fails to collect on the `format_status` import.
2. **The status row genuinely truncates on a narrow level.** At 40 columns, the longest message
   ("There are no stairs leading down here.", 38 chars) needs 38 + 1 + 18 = 57 columns beside
   `"Level 1  Seed 1234"`, so §4.2 clips it to `"There are no stairs l"`. This is correct and
   contractual — `status_right` always wins — but it means the default 80-column map is not
   generous, it is the *minimum* at which every message fits. Both behaviours are pinned
   (`test_run_shows_the_event_message_beside_the_status` at 80 columns,
   `test_a_message_too_long_for_the_row_is_clipped_so_the_status_survives` at 40). Worth knowing
   before anyone ships a narrower default.
3. **Leaving the dungeon draws no final frame.** `run` exits its loop the moment `running` goes
   `False`, so the `LEFT_DUNGEON` message is never rendered into the status row — it is printed
   by `play` after the terminal is restored, which is what §7.3 asks for. If a farewell frame on
   screen was also wanted, that is a `run` change and a contract question, not a bug.
4. **`saved` grows without bound** — one `LevelState` per depth visited, never evicted. RESEARCH
   §4 measured this as trivial (roughly 1760 coordinates per level; a 20-level dungeon is
   nothing), and eviction would break persistence, so this is deliberate.
5. `GameState` is unhashable, because `saved` is a `dict`. Frozen dataclasses generate a
   `__hash__`, so `hash(state)` raises `TypeError` at call time rather than at construction.
   Nothing needs it today; flagging in case anything downstream wants to put states in a set.
