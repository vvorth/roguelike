Behaviour as implemented:
- `render_to_lines` returns `level.height` map rows followed by one status row, every string
  exactly `level.width` characters. Map rows are that length by construction; the status row
  is `status[:width].ljust(width)`.
- A cell renders as `TILE_CHARS[level.tile_at(x, y)]` unless it is the player cell, which
  renders as `PLAYER_CHAR`. The player-cell branch short-circuits the `TILE_CHARS` lookup, so
  the player is drawn over a wall, a door, or a tile value with no glyph mapping at all.
- Out-of-bounds `player_pos` is turned into a `None` sentinel that no `(x, y)` tuple can equal,
  so the player is simply never drawn — no exception, no per-cell special case.
- `draw` calls `render_to_lines`, `stdscr.erase()`, then blits rows `< max_y` with each line
  truncated to `max_x`, dropping the final character of the last window row so the
  bottom-right cell is never written, then `stdscr.refresh()`. Every curses call is wrapped
  against `curses.error`. Returns `None`.
- `(y, x)` ordering appears only inside `draw`, in a block delimited by explicit
  `--- the one and only (y, x) region ---` comments, covering `getmaxyx()` and `addstr()`.
  Nothing else in the file — and per §0.1 nothing else in the codebase — uses that ordering.

Contract deviations: none.

Assumptions made:
- **Unmapped tile values.** §4 says a cell renders as `TILE_CHARS[level.tile_at(x, y)]`, so I
  render exactly that: a tile value absent from `TILE_CHARS` raises `KeyError`, loudly, the
  same way `tiles.tile_char` does. This cannot arise from a contract-conforming `Level`, and
  the player cell is exempt because the player glyph is chosen before the lookup happens —
  which is what makes "the player is drawn even if standing on an unexpected tile" true.
- **Malformed `player_pos`.** The signature says `tuple[int, int]`, so I unpack it directly. A
  non-pair raises `TypeError` from the unpacking rather than being silently ignored. This
  mirrors T01's identical choice for `Level.player_start`, and the contract specifies no rule
  for it. Only *out-of-bounds* positions are specified as "not drawn, no exception", and those
  are handled exactly as written.
- **`getmaxyx()` failing.** §4 mandates `erase()` before and `refresh()` after, and mandates
  swallowing `curses.error`. If `getmaxyx()` itself were to raise, I treat the window as
  0×0 (draw nothing) and still call `refresh()`, so the erase/refresh pairing is never broken
  by a swallowed error. A real window does not raise there.
- **Empty truncated lines are skipped.** In a window 1 column wide, the last-row guard reduces
  a line to the empty string; `addstr(row, 0, "")` is pointless, so it is skipped. Observable
  only through a fake window.
- **Clipping is width-then-guard.** Each line is truncated to `max_x`, and only the last
  *window* row (`max_y - 1`) loses its final character. Rows above it may use the full width;
  that is where curses actually tolerates the write.
- **The status line participates in clipping like any other row.** It is `lines[-1]`, so if
  the window is shorter than `level.height + 1` the status bar is what falls off the bottom.
  §4 gives no priority rule, and this is the only reading consistent with "draws only rows
  `< max_y`".

Open questions for integrator:
1. **Status bar vs. window height.** `draw` clips rows uniformly, so on a terminal exactly as

   "draws only rows `< max_y`") and not mine to make.
2. **`format_status` length.** §7 fixes the status text as
   `Seed: N  Pos: (x, y)  Turns: N  [q] quit` — 40-odd characters, comfortably inside the
   default 80-wide map, but on a narrow hand-built level it is truncated to `level.width` per
   §4. That is specified behaviour, not a defect; flagging it only because the truncation point
   is `level.width`, not the terminal width.
3. **Frame height is `level.height + 1`.** With the §3 defaults (80×22) that is 23 rows, one
   short of a classic 80×24 terminal, so nothing clips in normal use. A caller that grows
   `height` to fill 24 rows will silently lose the status line to the bottom-right guard on the
   last row; `main.py`'s `--height` handling may want to account for the extra status row.
