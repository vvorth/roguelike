## THE PUBLIC SURFACE — four downstream tasks import this

Everything below is in `__all__`, and `__all__` is asserted exactly by
`test_items_public_surface_is_exactly_the_contract_surface`. There is nothing else public.

```python
from roguelike.items import (
    # enums
    ItemKind,        # Enum:    WEAPON, SHIELD, CONSUMABLE
    WeaponKind,      # Enum:    MELEE, RANGED                     (unchanged from v5)
    DamageType,      # Enum:    SLASH, PIERCE, BLUNT
    Resistance,      # IntEnum: IMMUNE=0 < RESISTANT=1 < NORMAL=2 < VULNERABLE=3
    Grade,           # IntEnum: CRUDE=0 < STANDARD=1 < FINE=2
    # records, all frozen dataclasses
    Weapon,          # name, kind, damage_min, damage_max, range=1,
                     #   damage_type=DamageType.SLASH, grade=Grade.STANDARD
    Shield,          # name, block_chance, grade=Grade.STANDARD
    Consumable,      # name, heal=0, regen_turns=0, regen_magnitude=0
    Inventory,       # carried=(), melee=None, ranged=None, shield=None
    # constants
    CARRY_LIMIT,     # int, 20
    CLUB, DAGGER, SWORD, SLING, SHORTBOW, LONGBOW,        # Weapon
    BUCKLER, KITE_SHIELD, TOWER_SHIELD,                   # Shield
    POTION_OF_HEALING, BANDAGE,                           # Consumable
    # functions, all pure
    equip,           # (Inventory, item) -> Inventory
    unequip,         # (Inventory, slot: str) -> Inventory
    add,             # (Inventory, item) -> tuple[Inventory, bool]
    drop,            # (Inventory, index: int) -> tuple[Inventory, object | None]
)
```

**Constant names are mine to choose** — the contract names the item rows in prose only. They
are the upper-snake-case of the table's own names: `KITE_SHIELD`, `TOWER_SHIELD` and
`POTION_OF_HEALING` are the only ones where that is not a single word. `item.name` still
carries the display string (`"kite shield"`, `"potion of healing"`).

**Slot names are the three literal strings** `"melee"`, `"ranged"`, `"shield"` — the field
names of `Inventory`. `unequip` takes one of those; anything else is a `ValueError`.

**There is no collection constant** (no `WEAPONS`, no `ALL_ITEMS`, no by-grade index) and no
`kind_of(item)` helper. The brief calls extra surface a defect, so T34 (loot) builds its own
tables from the eleven constants above, and callers classify with `isinstance(item, Weapon)` /
`Shield` / `Consumable`. `ItemKind` is declared as the shared vocabulary for those three
categories; no record carries a `kind` field of that type, because the contract's dataclasses
do not have one.

### The numbers, untouched

`DAGGER` is 2–5 and `SHORTBOW` is 1–4, exactly as v5 shipped them. They are asserted by two
tests named `test_the_dagger_is_2_to_5_and_must_never_be_retuned` and
`test_the_shortbow_is_1_to_4_and_must_never_be_retuned`, so any retune is loud in the failure
output. Every other row of §25.1's three tables is asserted literally, field by field
(damage, type, grade, range for six weapons; block and grade for three shields; both
consumables). Shields are 10/18/25, not the 15/25/35 an earlier draft proposed.

`Resistance` is declared here and applied nowhere here — the multiplier is T32's, on the raw
roll (§26.2); the per-species table is T33's (§26.3). Nothing in this module does arithmetic
on a `Resistance` or a `Grade`; grade is a label, never a modifier.

## Assumptions — the four places §25 is silent

These are decisions, not deviations; each is tested, and each is the one a downstream caller
is most likely to trip over.

1. **`equip` on a non-equippable item raises `ValueError`.** §25.2 gives a slot rule for
   `Weapon` and `Shield` only. A `Consumable` (or any other object in the pack) has no slot,
   so `equip(inv, POTION_OF_HEALING)` raises rather than silently doing nothing. **T36:** the
   inventory screen's `e` key means "equip *or use*" (§7.17) — the *use* branch is yours, and
   you must dispatch on the item type before calling `equip`, not call `equip` and catch.

2. **`unequip` into a pack already at `CARRY_LIMIT` is a no-op**, returning the inventory
   unchanged with the slot still filled. It is the only operation that grows `carried`, and
   §25.2 says the pack holds *at most* 20. Keeping the cap true beat both alternatives
   (exceeding 20, or raising an error §11 does not list). **T36:** a player with a full pack
   cannot go bare-handed; if that needs a message, the check is
   `len(inv.carried) >= CARRY_LIMIT`.

3. **`unequip` with an unrecognised slot name raises `ValueError`.** A wrong string is a
   caller bug, not a game state.

4. **A negative `drop` index counts as out of range**, returning `(inventory, None)` rather
   than indexing from the end. The index comes from a letter on the inventory screen, so only
   a bug produces a negative one, and dropping the wrong item is worse than dropping none.

Two smaller behaviours worth stating, both tested:

- **`carried` is searched by equality**, so `equip` on one of two identical daggers removes
  exactly one of them, and `equip` never changes the pack's length (the displaced item is
  appended to the end of `carried` after the equipped one is removed).
- **`add` returns the *same* object** — not a copy — when the pack is full, alongside `False`.

imports only `dataclasses` and `enum`.
