**The exact call the game loop must now make:**

```python
from roguelike.render import Chrome, NpcGlyph, render_to_cells

npcs = tuple(
    NpcGlyph(position=n.position, glyph=SPECIES_DATA[n.species].glyph,
             species=SPECIES_DATA[n.species].name)
    for n in state.npcs
    if n.position in state.visible          # optional pre-filter; render_to_cells also
)                                            # enforces "visible only" itself either way

target = None
if state.targeting is not None:
    target = state.targeting.targets[state.targeting.index]

cells = render_to_cells(
    level, player_pos, visible, explored, open_doors, chrome,
    npcs, target,          # or npcs=npcs, target=target — both positions are last, both optional
)
```

Everything else (`to_lines`, `init_colors(colors=None)`, `draw(stdscr, cells)`) is unchanged.
`init_colors` must still be called once, after curses is up, exactly as before — it now also
allocates one colour pair per NPC species, transparently.

**How a species selects its colour (my design, since the brief left it open):** `NpcGlyph`
and `style.attr_for` both take `species` as a **plain lower-case string**, not
`npc.Species` — because neither `render.py` nor `style.py` may import `npc.py` (CONTRACT-v5
§10 v5). The string is exactly the value already sitting in `npc.SpeciesData.name`
(`"rat"`, `"jackal"`, `"giant bat"`, `"cave snake"`), so `game.py` passes
`SPECIES_DATA[npc.species].name` straight through with no translation table of its own.
`style.py` keeps a private `_NPC_COLORS_256: dict[str, int]` mapping those four strings to
250/173/140/70; an unrecognised or missing species degrades to `-1` (terminal default)
rather than raising, matching the module's existing "degrade, never crash" discipline.
`render.py` keeps its own small private tuple `_NPC_SPECIES = ("rat", "jackal", "giant bat",
"cave snake")`, used only so `init_colors` knows how many curses pairs to pre-allocate
(color pairs must be allocated once, in `init_colors`, never in `draw`, never per frame —
an existing, still-enforced rule). This duplicates the four species names between the two
files rather than exporting a shared constant from `style.py`; I judged that a smaller
surface change than adding new public API to `style.py` beyond what the contract specifies
(`Role.NPC` and `attr_for`'s new parameter). `draw()` looks NPC attributes up in a new
module-level `_NPC_ATTRS: dict[str, int]` (keyed by species) instead of `_CELL_ATTRS`
(keyed by `(Role, Visibility)`), because two species at the same visibility need different
colours — `(Role, Visibility)` alone can't express that.

Drawing order inside `render_to_cells` (all four steps happen in this fixed sequence):
1. terrain, from `visible`/`explored`/unseen exactly as before;
2. each `NpcGlyph`, only if `npc.position in visible` — **never `explored`**;
3. the player, unconditionally, so it always wins over an NPC on the same cell;
4. the ranged-target cell, if any, gets `reverse=True` via `dataclasses.replace` — this
   never touches `char`, so a targeted monster keeps its species glyph, not a cursor glyph.

Contract deviations: none. I re-read CONTRACT-v5 §4/§15 v5, CONTRACT-v3 §4, and
CONTRACT-v2 §15 line by line against the final diff before writing this report.

Assumptions made:
1. **Species identity is a plain string**, not `npc.Species` — required by the import-graph
   ban, and it is the natural key given `npc.SpeciesData.name` already exists in that exact
   form. Documented above and in both modules' docstrings.
2. **Unrecognised/missing species at `colors=256` degrades to `Attr(-1)` rather than
   raising.** Not specified by the contract or brief; I chose the same "never crash"
   discipline `attr_for` already uses everywhere else on this ladder. Only reachable by a
   caller bug (a species outside the bestiary), so it is defensive, not a normal path.
3. **`NpcGlyph`/`target` positions are bounds-checked with `level.in_bounds`, exactly like
   `player_pos` already was**, so an out-of-bounds NPC or target is silently not drawn
   rather than raising — consistent with the existing player behaviour and the "never
   raises" discipline the whole module already follows.
4. **The ranged-target highlight is applied last, after terrain, NPCs and the player**, so
   it can sit on top of any of them without ever altering `char`. `Chrome`'s two rows are
   never touched by it, since `target` addresses map coordinates and map rows only ever
   sit at `cells[1..height]`.
5. `_NPC_SPECIES` in `render.py` and `_NPC_COLORS_256`'s keys in `style.py` are the same
   four literal strings, kept in sync by hand and pinned by tests on both sides
   (`test_npc_species_colours_256` in `tests/test_style.py`,
   `test_init_colors_populates_npc_attr_table_for_every_species` in `tests/test_render.py`)
   — a drift between them would fail loudly rather than silently mis-colour a monster.

Open questions for integrator:
1. **Filtering `npcs` to `visible` before the call is optional, not required.**
   `render_to_cells` re-checks `position in visible` itself (that is the whole point of the
   headline rule being enforced inside the pure function, not by caller discipline), so
   `game.py` may simply pass `state.npcs` translated to `NpcGlyph` unfiltered every frame if
   that is simpler to wire up. Either way is correct; passing the full list is one line
   shorter.
2. **`Targeting.targets[index]` must be resolved to a plain `(x, y)` before the call.**
   `render.py` cannot accept `game.Targeting` itself (it may not import `game.py`), so the
   integrator computes `target = state.targeting.targets[state.targeting.index] if
   state.targeting else None` at the call site, as shown above.
3. **A dead/vanished target is not this module's problem.** CONTRACT-v5 §7.10 says
   targeting is rebuilt and the shot cancelled if the selected NPC is gone by the time `FIRE`
   resolves — that bookkeeping lives entirely in `game.py`. `render_to_cells` will happily
   highlight any `target` coordinate whether or not an NPC currently stands there (see
   `test_target_on_a_terrain_cell_highlights_it_without_changing_its_glyph`), which is
   correct since a target's death this same tick is exactly the kind of thing `game.py`
   is responsible for clearing before the next frame is built.
4. **`NpcGlyph.glyph` and `.species` are the integrator's job to source correctly** —
   `render.py` never validates that `glyph` matches `species` or that `species` is one of
   the four known strings; an unrecognised species just degrades gracefully in colour
   (assumption 2 above) rather than raising, so a typo there is a silent colour bug, not a
   crash. `game.py` sourcing both from the same `SPECIES_DATA[npc.species]` entry (as shown
   in the call-site example above) keeps them consistent by construction.
