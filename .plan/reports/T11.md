Contract deviations: none from CONTRACT-v2 §4/§15 or the retained v1 §4 rules. One
necessary implementation nuance, not a deviation from any binding behaviour: Python's
stdlib `curses.init_pair` raises `ValueError` (not `curses.error`) when curses has never
been initialised at all — it validates the pair number against `curses.COLOR_PAIRS`,
which defaults to `-1` pre-init, before making the underlying C call. Confirmed by hand:
`curses.start_color()`/`use_default_colors()`/`color_pair()` all raise `curses.error`
("must call initscr() first") with no TTY, but `init_pair()` specifically raises
`ValueError` instead. `init_colors`'s `curses.init_pair` call is wrapped in
`except (curses.error, ValueError)` rather than `except curses.error` alone, so the
"never call `curses.initscr`", "never raise", "must pass with no TTY" rules all still
hold — verified end to end: the full suite passes under pytest with stdin from
`/dev/null` and curses genuinely never initialised.

Assumptions made:
- Colour-pair allocation covers exactly 5 `(Role, Visibility)` combinations —
  `(TERRAIN, VISIBLE)`, `(TERRAIN, EXPLORED)`, `(DOOR, VISIBLE)`, `(DOOR, EXPLORED)`,
  `(PLAYER, VISIBLE)` — matching RESEARCH-v2 §3's "all five proposed pairs". `UNSEEN` is
  never allocated (never drawn, and `style.attr_for` raises for it); `(PLAYER, EXPLORED)`
  is never allocated either, since the player is always `VISIBLE` and `attr_for` raises
  for that combination too.
- Chose to bake `A_BOLD` (player) and `A_DIM` (sub-256-colour `EXPLORED`) into the
  module-level attribute dict inside `init_colors`, rather than computing them inside
  `draw` from a role/visibility check. The brief's constraint that "colour-pair
  allocation happens once ... never inside draw" and that draw must do "no visibility
  logic" reads more consistently this way: `draw` becomes a pure `dict.get` plus
  `addstr`, with zero conditionals on `Role`/`Visibility`/`colors`. §4.3's prose ("plus
  `A_BOLD` for the player and `A_DIM` for `EXPLORED`...") is satisfied either way; this
  reading keeps *all* per-cell-kind decisions inside the "once at startup" function.
- `draw` writes one character per on-screen cell (`stdscr.addstr(y, x, cell.char, attr)`)
  rather than building whole-line strings as v1 did. This follows directly from cells now
  carrying independent per-cell attributes — a single addstr call can only carry one
  attribute — and it makes the bottom-right-cell guard trivial and exact: skip writing
  exactly `(max_y-1, max_x-1)`, which is behaviourally identical to v1's "drop the last
  char of the last line" rule for that one cell, generalised to per-cell writes. Confirmed
  against the acceptance criteria (clip rows beyond `max_y`, truncate columns beyond
  `max_x`, never write the bottom-right cell, swallow `curses.error` from every call,
  survive 1×1 and 0×0 windows) — all covered by dedicated tests using a hand-written
  `FakeWindow` (extended from v1's to accept an `attr` 4th argument and record it).
- `render_to_cells` computes `Role` for map cells via `style.role_for(tile)` (reusing the
  one function that owns that mapping) rather than re-deriving "DOOR tile → Role.DOOR,
  else Role.TERRAIN" locally; for `UNSEEN` cells the role is hardcoded to `Role.TERRAIN`
  regardless of the underlying tile, per the brief's explicit rule ("else → UNSEEN,
  char=" ", role=TERRAIN") — this is intentional and not routed through `role_for`,
  since an unseen door must still report `Role.TERRAIN`, not `Role.DOOR`.
- Added a source-level test (`test_render_source_contains_no_bare_palette_colour_literals`)
  that greps render.py for the five binding 256-colour palette integers (250, 238, 180,
  94, 231) as a concrete proxy for the brief's "no bare colour integer" acceptance
  criterion, alongside the existing glyph-literal and import-graph source checks.
- `open_doors` entries for coordinates that aren't `DOOR` tiles are inert (never checked,
  since the open/closed branch is only taken when `role is Role.DOOR`) — covered by
  `test_open_doors_set_is_ignored_for_cells_that_are_not_doors`.
