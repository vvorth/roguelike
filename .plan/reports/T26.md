Assumptions made:
- **`_ENERGY_THRESHOLD = 100` is duplicated privately in `npc.py`** rather than imported, because
  `ENERGY_THRESHOLD` lives in `game.py` (§24.3) and `npc.py` may not import `game` (§10 v5). It is
  private and not exported, so there is only one *public* name for it. Starting energy is drawn
  from `range(0, 100)`, which is what the contract text and the brief both say literally.
- **A closed door is a legal wander target.** The brief's "Legality of a `MOVE` target" paragraph
  defines legality as `world.is_planning_passable` **and** not in `occupied`, with no exception for
  the wandering branch, so a wandering monster may bump a door open exactly as a hunting one does.
  (§24.2's prose for WANDERING says "passable orthogonal neighbour"; the brief's explicit legality
  rule is the more specific statement and is what the module implements.) `tests/test_npc.py`
  documents this in `test_a_closed_door_blocks_perception_and_an_open_one_does_not`.
- **The player's own cell is exempt from the `occupied` exclusion inside the `find_path`
  predicate.** The player is in `occupied` and is also the goal; excluding it would make the goal
  unreachable and turn every hunter into a waiter. The exemption can never leak into the returned
  step, because `path[1]` is adjacent to the NPC and an adjacent player was already answered with
  `ATTACK` before any search runs.
- **Contention between two NPCs is resolved by the caller's ordering, not by `plan_action`.**
  `plan_action` is pure and sees one NPC at a time, so "two NPCs do not both get the same cell"
  is only true if `game.py` folds each accepted move into `occupied` before planning the next NPC.
  That is the convention `test_two_npcs_contending_for_one_corridor_cell_do_not_both_get_it`
  models, and it is the only assumption in this report that the integrator must actually honour in
  code. See "Open questions" below.
- `spawn_npcs` terminates **structurally**, not by a retry budget: each of the at most six passes
  picks from the list of still-legal cells and then filters that list, so the work is bounded by
  `MONSTERS_PER_LEVEL * len(candidates)` on every input including a map where nothing fits. There
  is no rejection sampling to spin on.

## Where the WANDERING → HUNTING transition is expected to happen

`plan_action` is pure. It **never writes `ai_state` or `memory`** and returns only an `NpcAction`.
Both fields are `game.py`'s to maintain, and the precise expectation is:

1. **Perception is evaluated once per NPC action, by `game.py`, using the same rule `plan_action`
   uses internally:**
   ```python
   seen = (max(abs(npc.position[0] - player[0]), abs(npc.position[1] - player[1]))
           <= npc_module.PERCEPTION_RADIUS
           and fov.has_line_of_sight(level, open_doors, npc.position, player))
   ```
   Argument order is `(observer, target)` and **the NPC is the observer** (§14 v5 — permissive LOS
   is measurably asymmetric, 2 of 720 cell pairs disagree, so swapping these is a behaviour change,
   not a refactor).
2. **`WANDERING` + `seen` → `HUNTING` with `memory = 0`.** `plan_action` already *behaves* as
   though this switch has happened: given a wandering NPC that can see the player it returns the
   hunting action immediately (`ATTACK` if adjacent, else the `MOVE` along the path) and does not
   waste the turn shuffling. So the state write is bookkeeping for *subsequent* turns; the current
   turn is already correct whether or not `game.py` writes it before or after calling
   `plan_action`. Tested by `test_wandering_hunts_the_moment_the_player_is_in_plain_sight_within_radius`
   and the eight-way `test_wandering_with_the_player_adjacent_and_in_sight_also_attacks`.
3. **`HUNTING` + `seen` → `memory = 0`** (the trail is fresh again).
4. **`HUNTING` + not `seen` → `memory + 1`.** Once `memory > FORGET_TICKS` (5) the NPC reverts to
   `WANDERING` with `memory = 0`. Counting is per NPC *action*, not per world tick — a bat at speed
   180 acts twice on some ticks and forgets correspondingly sooner, which is the behaviour the
   energy model in §24.3 implies. If the integrator prefers per-tick counting, that is a `game.py`
   decision and nothing in `npc.py` changes; state the choice in `game.py`'s docstring either way.
5. **`WANDERING` + not `seen`** — nothing changes; `memory` stays where it is (it is only ever read
   while `HUNTING`).

`FORGET_TICKS` is exported for exactly step 4 and `npc.py` never reads it itself.

## Measured planning cost for 6 hunters

Full 80×22 generated levels, six hunters spawned by `spawn_npcs` and forced to `HUNTING`, each
planning a fresh `find_path` to `level.player_start` with all six positions plus the player in
`occupied`. Best of 20 passes, per level seed:

| Level seed | 6-hunter pass | per hunter |
|---|---|---|
| 21 | 12.22 ms | 2.04 ms |
| 22 | 4.49 ms | 0.75 ms |
| 23 | 8.67 ms | 1.45 ms |
| 24 | 8.57 ms | 1.43 ms |
| 25 | 3.89 ms | 0.65 ms |

Median **8.57 ms per pass, ~1.43 ms per hunter**. That is above RESEARCH-v5 §8's 0.5 ms reference
because these hunters are placed by the spawn rule — never closer than 8 cells from the player and
usually far across the map — which is close to A\*'s worst case on this map size; the reference
figure is a shorter search. It is still comfortably inside the 50 ms budget with ~4× headroom, and
the turn loop pays it once per world tick. `test_planning_six_hunters_on_a_full_level_is_well_under_fifty_milliseconds`
takes best-of-5 and asserts `< 50 ms`. Wandering costs a fraction of this (no search at all — the
Chebyshev pre-check rejects before `has_line_of_sight` is ever called).

## Confirmation that the two spawn radius rules hold across the seed sweep

Sweep: **50 level/seed combinations, 300 monsters** — seeds 0–29 at the default 80×22, seeds
100–109 at 60×30, and seeds 100–109 at 100×25.

- Every run placed **exactly 6** NPCs (`counts == {6}`); no real generated level ever fell short.
- **Minimum observed Chebyshev distance from `level.player_start`: 8** — the rule's exact bound,
  hit but never violated.
- **Minimum observed Chebyshev distance between any pair of spawned NPCs: 5** — likewise exactly
  the bound, never violated. (`itertools.combinations` over all 15 pairs per level, 750 pairs.)
- Every position passable with an **empty** `open_doors` set, and never a `DOOR` tile.
- `actor_id`s are `1..6`, distinct, in tuple order; `hp == derive(species.stats).max_hp` for every
  monster; `status_effects == ()`; `ai_state is WANDERING`; `memory == 0`.
- All four species appear across the sweep.

**Energy is staggered (the lockstep-pack trap):** across the 300 spawned monsters, **95 distinct
energy values**, spanning 0–99, with only 2 monsters at exactly 0. Every value lies in
`range(0, 100)`, and every level in the sweep produced more than one distinct energy among its six
monsters. Asserted directly, including the explicit `not all(e == 0 for e in energies)`.

**Hostile maps terminate with fewer NPCs**, under a strict wall-clock guard:
- 5×5 all-floor with `player_start` at the centre → `()` (every cell is inside the safe radius), in
  well under 1 s.
- A 20-cell 1-wide corridor → 2 or 3 NPCs over 50 seeds; 50 calls complete in ~4 ms, asserted
  `< 2 s`. The safe-radius and separation rules are re-asserted on the short results, so the count
  is never made up by relaxing a rule.
- An all-wall level, a 1×1 level, a 40×1 strip, a 1×40 strip and a 3-wide comb → never raises,
  never exceeds 6, all 50 calls under 2 s.

Open questions for integrator:

1. **`game.py` must fold each accepted NPC move into `occupied` before planning the next NPC.**
   `plan_action` cannot prevent two monsters from being handed the same empty cell, because it is
   pure and sees one NPC at a time. Plan in `actor_id` order (§24.3 already requires that order),
   and rebuild `occupied` after each accepted move. If a move is rejected downstream (a door bump
   that consumes the action instead), do **not** add the destination to `occupied`.
2. **`memory` counting: per action or per world tick?** See step 4 above. `npc.py` is indifferent;
   pick one and write it down, because a bat at speed 180 forgets twice as fast under per-action
   counting.
3. **Who calls `spawn_npcs`, and with which generator?** §24.4 says "the level's own seeded
   `Random`", so I expect `game.py` (not `generator.py`) to call it once when a `LevelState` is
   first created, with a generator derived from `level.seed`, and to store the result in
   `LevelState.npcs` (§24.5). `spawn_npcs` never creates or stores a generator itself.
4. **`first_actor_id` across levels.** It defaults to 1 on every level, so NPC ids are only unique
   *within* a level. If the roll-seed derivation in §0.12 needs ids unique across the whole
   dungeon, pass a running counter as `first_actor_id`; `spawn_npcs` supports it and it is tested.
   Otherwise ids collide between floors, which is harmless only if `roll_seed` also mixes in depth.
5. **Bump-to-open on a door.** `plan_action` returns `MOVE` onto a closed door because
   `is_planning_passable` accepts it. `game.py` must turn that into "open the door, consume the
   action, do not move" and emit `DOOR_OPENED` **only if the door is in the player's `visible` set**
   (§24.2, §16.1) — otherwise off-screen monsters spam the message line.
6. **`ATTACK` targets a coordinate, not an actor.** `NpcAction.target` is the player's cell.
   `game.py` resolves it against whoever stands there; `npc.py` cannot reference `combat` or the
   player type without breaking the import graph.
