## Segment-clearance method chosen

**Exact integer Amanatides–Woo grid traversal in doubled coordinates.** Every coordinate
that matters — cell edges, the eye at a cell centre, side midpoints — is a multiple of
0.5, so everything is doubled once and the entire traversal runs in `int`. **There is no
floating point anywhere**, hence no epsilon, no tie-breaking fudge, and exact lattice-point
detection (which the diagonal-corner rule depends on being exact).

The eye doubles to `(2*ox+1, 2*oy+1)` — odd in both axes, so it never starts on a grid
line. Grid lines sit at even doubled coordinates, so from an odd start the first crossing
in each axis is 1 doubled unit away and each later one is 2 further: the *k*-th crossing
along x is at `t = (2k-1)/|dx|`. Ordering two crossings is then one integer
cross-multiplication (`nx*ady` vs `ny*adx`), and "is this crossing before the sample
point" is one integer comparison (`nx < adx`). Equality of the two products is exactly the
lattice-point case. I chose this over dense sampling because dense sampling cannot decide
the diagonal-corner rule correctly at all — the rule is about a measure-zero event — and
over `Fraction`, which is exact but ~50x slower.

I did use the Fraction approach as the *independent* reference implementation in the test
file, so the two never share code.

## Cost at radius 20 on an 80x22 level

Measured on this machine with `.venv/bin/python`:

| Case | ms/call |
|---|---|
| Generated 80x22 (seed 1234), from `player_start` | **2.06** |
| Same level, averaged over all 663 open cells | **2.57** |
| Wide-open 80x22 floor, eye at centre (830 cells visible) | 1.49 |
| 20% random walls, 80x22, eye at centre (worst case found) | 2.90 |

So **~2–3 ms per move**, against CONTRACT-v2 §14.2 F9's ~15 ms estimate and a ~100 ms
human-keypress budget. Two things account for beating the estimate, neither of which is an
approximation: the integer DDA replaces per-step float work, and each call takes one local
snapshot of `world.is_transparent` over the candidate box (grown by 1) instead of calling
through the predicate ~400k times. The snapshot lives and dies inside the call — it is not
a cache and there is nothing to go stale. **The algorithm is exactly the one §14.1
specifies; no `fast=` mode, no hybrid, no shadowcasting.**

Contract deviations: none. Two points where §14.1 needed a reading rather than a
transcription, both resolved in favour of the guarantee the contract states more strongly,
and both pinned by tests:

1. **The diagonal-corner rule applies only at lattice points strictly interior to the
   segment (`0 < t < 1`), not at a sample point the segment terminates on.** §14.1 says a
   segment is blocked "where a segment **passes through** a grid lattice point"; a segment
   that *ends* at one does not pass through it. This is forced, not preferred. Standing in
   the middle of a room, the *only* clear line to a **corner cell of the wall ring** is the
   one ending exactly on the room's inner corner, whose two flanking cells are the two wall
   runs meeting there. Applying the rule at the endpoint punches all four corners out of
   every room — precisely the ragged-wall artifact F6 calls a defect and the brief calls
   "the entire reason the permissive rule exists". The two cases are geometrically
   identical up to relabelling, so no rule can block one and allow the other; F6 is the
   stated guarantee, so it wins. The visible cost is one cell: the cell diagonally beyond a
   two-wall join, whose own corner *is* the join tip, is visible. That is faithful to user
   rule #5 ("visible if any side or corner is in direct eye sight" — the eye really does
   see that point), and **nothing beyond it is visible**: verified exhaustively on a
   full-diagonal wall, the far-side cells ever visible from any near-side eye are exactly
   the corner-touching family `{(k-1, k)}` and `max(y - x) == 1`. Sight never travels
   *through* the join.

2. **F1 beats F2 for an out-of-bounds origin.** F1 says the origin is "always" in the
   result "even standing on a wall or off-map terrain"; F2 says every returned cell is in
   bounds. These collide only when the caller passes an out-of-bounds origin. I include the
   origin unconditionally, so `compute_visible` never returns an empty set and never
   raises for a bad position. `Level.__post_init__` already forbids an out-of-bounds
   `player_start`, so game.py cannot reach this state.

Assumptions made:
- **F4 is an emergent property of the §14.1 rule on realistic maps, not a theorem — and I
  did not "fix" that.** The eight sample points sit on the target's *boundary*; its centre
  is not among them, so a target reachable only through a slit narrower than the target's
  own half-width can have a clear centre ray and eight blocked sample rays. I found
  **exactly one** such cell in a 760-case adversarial sweep (45%-wall noise with random
  doors), and **zero** across 360 generated-level origins at radii 3/8/20, zero on rooms,
  pillars, corridors and door levels. Adding the centre as a ninth sample point would make
  F4 a theorem, and I deliberately did **not** do it: §14.1 fixes the rule at eight points,
  and a ninth would reveal cells the rule does not grant — over-showing, which F9 calls a
  defect. Reported rather than papered over.
- The test file's centre-to-centre reference reads "unobstructed" **conservatively**: the
  segment must not *touch* an opaque cell at all, so a ray that slips past only by passing
  exactly through a wall's corner point counts as obstructed. That is what centre-to-centre
  shadowcasting does (F4 names shadowcasting as the comparison) and it is the honest
  reading of "unobstructed". Under this reading the subset property holds on **every** case
  I swept, including all 400 adversarial noise levels. Under the lenient reading it fails
  on ~13% of 45%-density noise maps via knife-edge rays that thread two wall corners
  exactly — never on a generated level.
- Test levels are hand-built from character grids via a local `make_level` helper (`#`
  wall, `.` floor, `+` door, `@` floor-and-player-start). The generator is never imported.
  Door open/closed comes solely from the `open_doors` argument, never from a second tile.
- A closed door separating exactly two open cells (T09 point 4) is relied on by one test
  and holds.
- `radius` is validated with `radius < 0`, so `True`/`False` behave as `1`/`0` rather than
  raising, consistent with the rest of the codebase's handling of bool-as-int.

Open questions for integrator:
1. **Cost is ~2–3 ms per move, not the ~15 ms F9 predicted.** Nothing was traded away for
   it — same rule, same eight points, exact arithmetic. If a later measurement is compared
   against F9's number, this is why it is lower. Budget is untouched: recompute-per-move in
   `game.step` is comfortable.
2. **The corner-touch cell is visible through a diagonal wall join**, by the reasoning in
   deviation 1. If the renderer or a play-test makes that look wrong, the fix is a contract
   decision, not a code change — the alternative costs F6, and F6 is the stated guarantee.
   Both behaviours are pinned by name in `tests/test_fov.py` so a change is loud.
3. **F4 is not guaranteed in the adversarial limit** (assumption 1). It holds on every
   generated level measured. If per-entity FOV or a hand-authored map ever arrives, re-check
   rather than assume.
4. `compute_visible` includes the origin even if it is out of bounds (deviation 2). If
   `game.py` prefers a hard failure there, that is a contract question — today `Level`
   forbids the state that would produce it.
5. The result is a `frozenset` of `(x, y)`; `render.render_to_cells` should treat "not in
   the set" as `UNSEEN`/`EXPLORED` per §4.1. FOV has no opinion on how anything looks, and
   returns no brightness, distance or timestamp — §14 grants none.
