## THE SIGNATURE DECISION — read this first

`tick_effects` now returns **three values, not a signed net**, per the brief's recommendation:

```python
def tick_effects(
    effects: tuple[StatusEffect, ...],
) -> tuple[tuple[StatusEffect, ...], int, int]:
    ...
    return surviving_effects, total_damage, total_healing
```

- `surviving_effects: tuple[StatusEffect, ...]` — unchanged from v5.
- `total_damage: int` — sum of `magnitude` over every `POISONED` entry that was ticked this
  call (including entries that dropped to `remaining_turns == 0` on this tick).
- `total_healing: int` — sum of `magnitude` over every `REGENERATING` entry that was ticked
  this call, same "still counts on the removing tick" rule.

`ENRAGED` entries (and any future kind nobody has added yet) are ticked — decremented and
dropped/kept exactly like the others — but contribute to **neither** total. They are a pure
duration flag; nothing applies `ENRAGED` yet, unchanged from T22.

`tick_effects(())` returns `((), 0, 0)`.

Why not a signed net: `POISONED` magnitude=2 and `REGENERATING` magnitude=2 ticking together
nets to 0, indistinguishable from "nothing happened." The game loop needs to say "you take 2
damage and heal 2" versus "nothing happens" as different messages, so both totals are reported
separately, always. This is exercised directly by
`test_poison_and_regeneration_coexist_and_are_distinguishable`.

**Both downstream callers (`combat.py`/`game.py` consumers of this function) must unpack three
values**, e.g. `surviving, damage, healing = tick_effects(effects)`.

## Public surface

```python
# roguelike/status.py — __all__ = ["StatusKind", "StatusEffect", "REGEN_TURNS",
#                                   "apply_effect", "tick_effects"]
class StatusKind(Enum):
    POISONED = auto()
    ENRAGED = auto()
    REGENERATING = auto()

@dataclass(frozen=True)
class StatusEffect:
    kind: StatusKind
    remaining_turns: int
    magnitude: int

REGEN_TURNS: int = 3     # unchanged from T22 — natural regen, unrelated to the bandage

def apply_effect(effects: tuple[StatusEffect, ...], new: StatusEffect) -> tuple[StatusEffect, ...]
def tick_effects(effects: tuple[StatusEffect, ...]) -> tuple[tuple[StatusEffect, ...], int, int]
```

`apply_effect`'s signature and behaviour are byte-for-byte unchanged from T22 — refresh-not-
stack applies identically to `REGENERATING` (re-verified with dedicated tests using that kind,
not just re-used poison tests) since the function never branches on `kind` at all.

Contract deviations: none. `REGEN_TURNS` stays 3 (natural healing, CONTRACT-v5 §22.4,
unrelated to the bandage's `regen_turns=5` from CONTRACT-v6 §25.1 — that number lives in
`items.py`'s `Consumable`, out of this module's scope, and nothing in `status.py` hardcodes
5 or 3-for-bandage anywhere).

Assumptions made:
- **`ENRAGED` contributes to neither total when ticked.** The contract doesn't specify this
  because nothing has ever ticked an `ENRAGED` effect before (T22 shipped it applied by
  nobody). The old code would have silently added its `magnitude` to `total_damage` — that
  was never exercised by a test and I judged it an accident of the old single-purpose
  implementation, not a specified behaviour worth preserving. Routing by kind explicitly (only
  `POISONED` → damage, only `REGENERATING` → healing, everything else → neither) is the
  reading that makes "the caller can tell them apart" (acceptance criterion) actually true, and
  is now itself tested (`test_enraged_contributes_no_damage_or_healing_when_ticked`) so it's a
  documented decision, not a silent one. If a future task wants `ENRAGED` to do something
  numeric on tick, this is the line to revisit.
- **`StatusEffect.magnitude` for `ENRAGED` is "conventionally 0"** per the updated docstring,
  but nothing enforces it — `tick_effects` ignores it regardless of value, so an `ENRAGED`
  effect with a nonzero `magnitude` doesn't crash, it's just inert. No validation was added
  since T22's original `StatusEffect` had none either and the brief doesn't ask for any.
