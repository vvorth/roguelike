fully open 80×22 map (worst case — no obstacles to prune the frontier) measured **~2.5 ms
median** over 20 runs in this environment. The coordinator's independent measurement on the

`RESEARCH-v4.md` §3's reference figure (0.235 ms) was measured on the real generated level,
which has walls that shrink the open frontier — an open 80×22 rectangle is close to the worst

**Re-planning every turn (T20/T21's stated approach) is safe.**

**How ties are broken (load-bearing for T20/T21's re-planning):** The open list is a `heapq` of
`(f_score, coord, g_score)` tuples. `f_score` and `g_score` are plain non-negative `int`s and
`coord` is an `(x, y)` tuple of `int`s, so every entry is totally ordered against every other —
ties on `f_score` are broken by comparing `coord` lexicographically (x first, then y), never by
insertion order, object identity, or set/dict iteration order. Neighbour expansion always walks
`DIRECTIONS` in its fixed compile-time order. Together this makes the result independent of
`PYTHONHASHSEED`, of the iteration order of the `goals` set, and of process/run identity —
confirmed by the coordinator's three-seed subprocess check. **A given `(passable, start,
goals)` triple always returns the exact same path**, which is what makes safe, cheap
re-planning every turn possible for TRAVEL/AUTO_EXPLORE/AUTO_WALK.

Two behaviours worth flagging explicitly for T20, since it will drive `find_path` with a
`passable` restricted to `explored` terrain and with `goals` built from a frontier set:
- **`start` not passable:** `find_path` never calls `passable` on `start` — only on cells being
  expanded *into*. So a start cell that `is_planning_passable` would reject does not block the
  search; every other cell on the returned path, including the first step taken off `start`, is
  still passable. This matters because T20's explored-only `passable` may be stricter at the
  character's exact cell than elsewhere.
- **Large `goals` (a whole frontier set):** the heuristic used during search is
  `min(octile(node, g) for g in goals)`, recomputed per expanded node, so cost scales as
  `O(nodes_expanded × |goals|)`. For a frontier set on an 80×22 map this stays well inside the
  5 ms budget (verified above), but it is a real cost, not free — if a future frontier set were
  pathologically large (thousands of cells) it would show up here first. No caching or
  memoization was added per the contract's explicit prohibition, so this cost is paid on every
  call by design.
